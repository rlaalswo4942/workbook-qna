# 7장. 고장 났을 때: 디버깅과 코드 읽기

> **이번 주 목표** 막혔을 때 **AI에게 떠넘기지 않고 원인을 좁혀 가는 법**을 익힌다. 이 수업에서 가장 오래 남을 기술이다.

---

## 1. 학습 목표

이 장이 끝나면 다음을 할 수 있다.

- 개발자 도구 콘솔을 열고 에러 메시지를 읽을 수 있다.
- 에러의 종류를 보고 원인을 짐작할 수 있다.
- `console.log`로 값을 추적해서 **어느 숫자가 잘못되었는지** 찾을 수 있다.
- 에러가 없는 버그("조용한 버그")에 접근하는 방법을 안다.
- AI에게 버그를 설명할 때 필요한 정보를 빠뜨리지 않는다.
- AI가 만든 코드를 구역으로 나눠 읽고, 핵심 부분을 설명할 수 있다.

---

## 2. 개념 설명

### 2.1 디버깅은 고치는 일이 아니라 찾는 일이다

버그를 만났을 때 초보자가 하는 행동은 대개 이렇다.

```
"안 돼요" → AI에게 전체 코드를 던진다 → AI가 뭔가 고친다
→ 다른 게 망가진다 → 또 던진다 → 코드가 점점 이해 불가능해진다
```

문제는 **고치려고 서두르는 것**이다. 고치기 전에 할 일이 있다.

> **디버깅의 90%는 "어디가 문제인가"를 찾는 일이고, 고치는 것은 마지막 10%다.**

위치를 알면 고치는 건 쉽다. AI도 "어디가 문제인지" 알려 주면 정확하게 고친다. 그래서 이번 주에 배우는 것은 **고치는 법이 아니라 좁히는 법**이다.

좁히는 질문은 네 개다.

| 질문 | 확인 방법 |
|---|---|
| ① 에러가 나는가, 안 나는가? | `F12` → Console |
| ② 언제 생기는가? | 시작할 때 / 특정 키를 누를 때 / 부딪힐 때 |
| ③ 어느 값이 이상한가? | `console.log`로 찍어 본다 |
| ④ 어느 줄부터 잘못되는가? | 값을 여러 곳에서 찍어 비교한다 |

### 2.2 개발자 도구 — `F12`

브라우저에서 `F12`(또는 `Ctrl+Shift+I`)를 누르면 창이 열린다. 탭이 여러 개지만 이 수업에서 쓰는 것은 둘이다.

| 탭 | 하는 일 | 쓰는 때 |
|---|---|---|
| **Console** | 에러와 `console.log` 출력 | **거의 항상 여기** |
| Elements | HTML 구조 확인 | canvas가 제대로 있는지 볼 때 |
| Sources | 코드 보기, 중단점 | 이 수업에서는 쓰지 않는다 |
| Network | 파일 불러오기 확인 | 이미지가 안 보일 때 가끔 |

**습관을 하나 만든다. 게임을 테스트할 때는 콘솔을 열어 둔다.** 그러면 에러가 생기는 순간을 바로 본다. 닫아 두면 "뭔가 이상한데" 상태로 한참을 헤맨다.

콘솔에 쌓인 내용은 왼쪽 위의 🚫 아이콘으로 지울 수 있다. **테스트 전에 한 번 비우고 시작하면** 지금 생긴 에러만 보여서 훨씬 명확하다.

### 2.3 에러 메시지 읽는 법

에러 메시지는 영어라서 겁나지만, 구조는 늘 같다.

```
Uncaught TypeError: Cannot read properties of undefined (reading 'x')
    at gameLoop (script.js:47)
    └─────────┘  └────────┘ └─┘
     어느 함수     어느 파일  몇째 줄
```

**세 가지만 보면 된다.**

1. **에러 종류** — `TypeError`, `ReferenceError` 등 (아래 표)
2. **설명** — 무엇이 문제인지
3. **`script.js:47`** — **몇째 줄인지**. 이 부분을 클릭하면 그 줄로 바로 간다

> **줄 번호를 클릭하는 습관을 들인다.** 에러 메시지만 읽고 코드를 뒤지는 사람이 많다. 클릭하면 문제의 줄이 바로 열린다.

**자주 보는 에러 네 가지**

| 에러 | 뜻 | 흔한 원인 |
|---|---|---|
| `SyntaxError` | **문법이 깨졌다** | 괄호나 중괄호가 안 맞는다. 보통 코드를 직접 고치다 생긴다 |
| `ReferenceError: X is not defined` | **X라는 이름을 모른다** | 변수 이름 오타, 또는 선언하지 않고 썼다 |
| `TypeError: Cannot read properties of undefined` | **없는 것의 속을 보려 했다** | 배열 번호가 범위를 넘었거나, `getElementById`가 못 찾았다 |
| `NaN` (에러는 아니지만) | **숫자가 아님** | 숫자에 글자를 섞어 계산했다. 화면에 `NaN`이 표시된다 |

**가장 자주 만나는 두 가지를 더 자세히 본다.**

**`ReferenceError: ballX is not defined`**

→ `ballX`라는 변수가 없다. 원인은 둘 중 하나다.
- **오타** — 선언은 `ballx`인데 쓸 때는 `ballX`라고 썼다 (대소문자 구분!)
- **선언 누락** — `let ballX = ...` 줄이 없거나 지워졌다

**`TypeError: Cannot read properties of null (reading 'getContext')`**

→ `canvas`가 `null`이다. 즉 **도화지를 못 찾았다.**
- `index.html`의 `id`와 `getElementById`의 이름이 다르다
- `<canvas>` 태그가 없다

이 두 에러가 전체의 절반 이상이다. **"이름을 못 찾았다"가 대부분의 원인**이라는 뜻이다.

### 2.4 `console.log` — 디버깅의 주역

에러 메시지는 "코드가 멈춘 곳"을 알려 준다. 그런데 **멈추지는 않고 결과만 이상한 경우**가 훨씬 많다. 그때 쓰는 것이 `console.log`다.

```javascript
console.log("플레이어 위치:", player.x, player.y);
console.log("적 개수:", enemies.length);
console.log("충돌 검사:", player.x, enemy.x, "충돌?", 결과);
```

4장에서 배운 관점이 여기서 힘을 발휘한다.

> **게임은 숫자 몇 개다. 화면이 이상하다면, 어느 숫자가 이상한 것이다.**

그러니까 **이상한 숫자를 찾으면 끝이다.** `console.log`는 숫자를 눈으로 보는 도구다.

**찍을 때 세 가지 요령**

**(1) 이름표를 붙인다**

```javascript
console.log(player.x);                 // 숫자만 나와서 뭔지 모른다
console.log("player.x =", player.x);   // 훨씬 낫다
```

**(2) 루프 안에서는 조건을 걸거나, 한 번만 찍는다**

게임 루프 안에서 그냥 찍으면 **1초에 60줄**이 쏟아져서 읽을 수 없다.

```javascript
if (keys["ArrowRight"]) console.log("오른쪽 키, x =", player.x);   // 키 누를 때만
```

또는 AI에게 요청한다.

```
console.log이 1초에 60번 찍혀서 읽을 수가 없어.
(어느 조건)일 때만 찍히게 바꿔 줘.
```

**(3) 범위를 반으로 좁힌다 (가장 강력한 기술)**

코드가 길어서 어디가 문제인지 모를 때 쓴다.

```
전체 구간에서 결과가 이상하다
  → 중간쯤에 console.log를 찍는다
     → 중간에서 값이 정상이면 → 문제는 뒤쪽에 있다
     → 중간에서 이미 이상하면 → 문제는 앞쪽에 있다
  → 남은 쪽의 중간에 또 찍는다
  → 몇 번만 반복하면 문제의 줄에 도달한다
```

이것을 **이분 탐색**이라고 부르는데, 이름은 몰라도 된다. **"반으로 잘라서 어느 쪽인지 본다"** 만 기억하면 된다. 프로 개발자도 가장 많이 쓰는 방법이다.

### 2.5 조용한 버그 — 에러가 없는데 이상할 때

이 수업에서 실제로 가장 많이 만나는 종류다. 에러는 없는데 결과가 틀린다. 몇 가지 유형과 접근법이 있다.

| 증상 | 의심할 것 | 확인 방법 |
|---|---|---|
| 안 보인다 | 좌표가 화면 밖 / 색이 배경과 같음 / 크기 0 | `console.log`로 좌표·크기 확인 |
| 안 움직인다 | 속도가 0 / 계산이 루프 밖에 있음 | 매 프레임 값이 변하는지 찍어 본다 |
| 너무 빠르다 | 루프가 두 개 돌고 있다 | `gameLoop()`를 두 번 부르지 않았는지 |
| 판정이 이상하다 | 히트박스가 그림과 어긋남 | **히트박스를 그려 본다** (6장에서 만든 `showHitbox`) |
| 점수가 폭주한다 | 매 프레임 증가 / 충돌이 반복 판정 | 증가하는 곳에 조건이 있는지 |
| 방향이 반대다 | 부호(`+`/`-`) 문제 | 5장에서 직접 실험해 봤다 |
| 재시작 후 이상하다 | `resetGame`에서 되돌리지 않은 값이 있다 | 상태 변수 목록과 대조 |

**가장 유용한 기법: 보이지 않는 것을 그려 본다.**

6장에서 히트박스를 테두리로 그렸다. 같은 방법을 다른 데도 쓸 수 있다.

```
AI에게 요청하는 예:
- "플레이어의 x, y 값을 화면 왼쪽 위에 작은 글씨로 계속 표시해 줘"
- "적의 개수와 현재 gameState를 화면에 표시해 줘"
- "디버그 정보를 showDebug 변수로 켜고 끌 수 있게 해 줘"
```

**화면에 숫자를 띄워 두면 콘솔을 안 봐도 상태가 보인다.** 플레이하면서 "아, 여기서 값이 튄다"를 바로 알 수 있다. 제출하기 전에 `showDebug`를 `false`로 끄면 된다.

### 2.6 AI에게 버그를 설명하는 법

AI는 **내가 준 정보 안에서만** 판단한다. "안 돼요"로는 추측밖에 할 수 없고, 추측으로 고치면 멀쩡한 코드가 망가진다.

**빠뜨리면 안 되는 다섯 가지**

| 항목 | 예 |
|---|---|
| ① **하려던 것** | "적에 부딪히면 게임 오버가 되게 하려 했다" |
| ② **실제로 일어난 것** | "부딪혀도 아무 일이 없다. 통과한다" |
| ③ **재현 조건** | "오른쪽 벽에 붙어 있을 때만 그렇다" |
| ④ **에러 메시지 원문** | 콘솔에서 **그대로 복사** (요약 금지) |
| ⑤ **이미 시도한 것** | "히트박스를 그려 봤더니 테두리가 어긋나 있었다" |

③번이 특히 강력하다. **"언제 생기는가"를 특정하면 원인이 거의 좁혀진다.** "오른쪽 벽에서만"이라면 경계 처리 쪽을 보게 된다.

⑤번도 중요하다. 시도한 걸 말하지 않으면 AI가 같은 걸 또 시킨다.

**추가로 붙이면 좋은 두 마디**

```
- 어느 부분만 고쳐야 하는지 먼저 말해 주고, 그다음에 고쳐 줘
- 다른 부분은 건드리지 마
```

첫 줄은 **내가 원인을 배우기 위한 것**이고, 둘째 줄은 **멀쩡한 코드를 지키기 위한 것**이다. 코드가 길어지는 7장 이후에는 둘째 줄이 특히 필요하다.

> **전체 코드를 통째로 붙이지 않는다.** 길면 AI가 엉뚱한 곳을 고친다. 관련된 함수 하나 정도만 붙이고, 어느 파일 어느 함수인지 말한다. 에이전트 모드에서는 "`checkCollision` 함수를 봐 줘"처럼 **이름으로 가리키면** AI가 직접 찾아 읽는다.

### 2.7 AI가 만든 코드 읽는 법

이제 `script.js`가 100~200줄이 되었을 것이다. 전부 이해할 필요는 없다. 하지만 **구조를 파악하고, 핵심 부분은 설명할 수 있어야** 한다. 이번 주 과제이고, 10장 발표에서도 필요하다.

**(1) 구역으로 나눠서 본다**

우리 게임의 코드는 거의 항상 이 순서로 되어 있다.

```
① 준비        canvas, ctx 가져오기
② 상태 변수   player, enemies, score, gameState ...
③ 이벤트      keydown, keyup, click ...
④ 함수들      checkCollision, resetGame, drawPlayer ...
⑤ 게임 루프   gameLoop — 지우기 / 계산 / 그리기
⑥ 시동        gameLoop();
```

**먼저 이 여섯 구역이 어디서 어디까지인지 표시해 본다.** 구조가 보이면 "고칠 곳"을 찾는 속도가 달라진다. 코드가 뒤섞여 있으면 AI에게 정리를 요청할 수 있다.

```
script.js를 아래 순서로 정리해 줘. 동작은 절대 바꾸지 말고 순서와 주석만.
① 준비 ② 상태 변수 ③ 이벤트 ④ 함수들 ⑤ 게임 루프 ⑥ 시동
각 구역 위에 주석으로 제목을 달아 줘.
```

**(2) 이름으로 짐작한다**

프로그래밍 코드의 이름은 대개 영어로 뜻이 드러난다.

| 이름 | 짐작 |
|---|---|
| `checkCollision` | 충돌을 검사(check)한다 |
| `resetGame` | 게임을 처음으로 되돌린다 |
| `spawnEnemy` | 적을 생성(spawn)한다 |
| `updateScore` | 점수를 갱신한다 |
| `isJumping` | 점프 중인가? (`is~`는 예/아니오 값) |

**이름만 보고 역할을 짐작한 뒤, 안을 읽어 확인한다.** 이 순서로 읽으면 훨씬 빠르다.

**(3) 지워 보고 확인한다**

1장부터 계속 쓴 방법이다. 모르겠는 줄은 **`//`로 잠시 끄고** 무엇이 달라지는지 본다. 커밋해 두었다면 안전하다.

**(4) AI에게 설명을 요청한다 — 단, 질문을 구체적으로**

```
❌ "이 코드 설명해 줘"                  → 뻔한 설명이 길게 나온다
⭕ "이 함수에서 && 로 이어진 네 조건 중, 세 번째 조건이 없으면
   어떤 경우에 잘못 판정되는지 예를 들어 설명해 줘"
```

**질문이 구체적일수록 이해가 깊어진다.** 그리고 이런 질문을 할 수 있다는 것 자체가 코드를 읽고 있다는 증거다.

### 2.8 다섯 단계 디버깅 절차

막혔을 때 이 순서로 한다. 책상 앞에 붙여 둘 만한 것이다.

```
1. 멈춘다        — AI에게 던지기 전에 손을 뗀다
2. 본다          — F12 Console. 에러가 있는가?
3. 좁힌다        — 언제 생기는가? 어느 값이 이상한가? (console.log)
4. 설명한다      — 하려던 것 / 실제 / 재현 조건 / 에러 원문 / 시도한 것
5. 고친다        — 범위를 지정해서 요청하고, 결과를 확인한 뒤 커밋
```

**3번을 건너뛰고 4번으로 가는 것이 가장 흔한 실수다.** 좁히지 않은 채 설명하면 결국 "안 돼요"와 다를 게 없다.

## 3. 따라 하기 실습

작업 폴더는 **`my-game`** 이다.

> **시작 전에 커밋한다.** 소스 제어 → `7장 시작 전 상태` → Commit.

### Step 1. 에러를 일부러 만들어서 읽어 본다 (10분)

에러 메시지와 친해지는 것이 목적이다. **하나씩 하고, 콘솔을 읽고, 바로 되돌린다.**

**실험 1 — `ReferenceError` 만들기**

1. `script.js`에서 `player`를 쓰는 줄 하나를 찾아 `playerr`로 바꾼다 → 저장
2. `F12` Console을 본다 → `ReferenceError: playerr is not defined`
3. **줄 번호를 클릭한다** → 그 줄로 이동하는 것을 확인한다
4. 되돌린다

**실험 2 — `TypeError` 만들기**

1. `getElementById("game")`을 `getElementById("gamee")`로 바꾼다 → 저장
2. 콘솔 → `Cannot read properties of null (reading 'getContext')`
3. **"null의 속을 보려 했다 = 도화지를 못 찾았다"** 로 해석되는 것을 확인한다
4. 되돌린다

**실험 3 — `SyntaxError` 만들기**

1. 아무 함수의 닫는 중괄호 `}` 하나를 지운다 → 저장
2. 콘솔 → `SyntaxError` / `Unexpected end of input`
3. **게임이 아무것도 그리지 않는다**는 것을 확인한다. HTML과 CSS는 멀쩡하므로 canvas 테두리는 보이지만, `script.js`는 **한 줄도 실행되지 않는다.** 문법이 깨지면 코드 전체가 통째로 무효다
4. 되돌린다 (`Ctrl+Z` 또는 2장의 되돌리기)

**실험 4 — `NaN` 만들기**

1. 점수에서 글자를 빼게 만든다 — 예: `score = score - "a"`
2. 화면의 점수 표시를 본다 → **`NaN`** 이 뜬다
3. 이번에는 `score = score + "1"` 로 바꿔 본다 → `NaN`이 아니라 **`"01"`, `"011"` 처럼 글자가 이어붙는다**
4. 되돌린다

> **둘의 차이가 중요하다.** `+`는 글자 이어붙이기로 동작해서 **에러도 `NaN`도 없이 조용히 틀린다.** 점수가 `"0111"`처럼 보이면 숫자와 글자가 섞인 것이다. 8장 `localStorage`에서 이 문제를 다시 만난다.

> **이 네 가지가 앞으로 만날 에러의 대부분이다.** 일부러 만들어 보면, 실제로 만났을 때 당황하지 않는다.

### Step 2. 숨은 버그 찾기 게임 (15분) — 이번 주 핵심 실습

**게임 본체를 건드리지 않기 위해 연습용 복사본을 만든다.**

1. AI에게 요청한다

```
지금 게임의 index.html, style.css, script.js를 합쳐서
debug-practice.html 이라는 하나의 파일로 복사해 줘.
(연습용이라서 원본은 그대로 둬야 해.)
```

2. 그 파일이 Live Server로 정상 작동하는지 확인한다
3. 이제 버그를 심게 한다

```
debug-practice.html 안에 버그 3개를 심어 줘.

조건:
- 1개는 콘솔에 에러가 나는 버그
- 2개는 에러 없이 동작만 이상해지는 버그
- 어떤 버그를 심었는지는 알려 주지 마
- 버그가 심어진 줄에 "여기가 버그" 같은 주석을 달지 마
- 게임이 아예 안 뜨는 수준으로 심하게 심지는 말아 줘
```

4. **스스로 찾는다.** 규칙은 하나다 — **AI에게 어디가 버그인지 묻지 않는다.**

찾는 순서는 2.8의 절차를 따른다.

- [ ] `F12` Console을 본다 → 에러 버그 1개는 여기서 잡힌다
- [ ] 줄 번호를 클릭해서 그 줄을 본다
- [ ] 나머지 2개는 플레이하면서 "무엇이 이상한가"를 말로 적어 본다
- [ ] 이상한 값에 `console.log`를 찍어 확인한다
- [ ] 찾은 버그를 **직접 고친다**

5. 세 개를 다 찾았다고 생각하면 그때 확인한다

```
내가 찾은 버그는 이거야.
1) (설명)
2) (설명)
3) (설명)
맞는지 알려 주고, 못 찾은 게 있으면 그게 어디인지 알려 줘.
```

> **다 못 찾아도 괜찮다.** 두 개만 찾아도 충분하다. 중요한 것은 **찾는 과정을 거쳤다는 것**이고, 그 과정이 이번 주 회고의 내용이 된다.

### Step 3. 디버그 표시를 만든다 (8분)

내 게임에 **상태를 눈으로 보는 장치**를 붙인다. 앞으로 계속 쓴다.

```
내 게임에 디버그 표시를 추가해 줘.

- showDebug 라는 변수로 켜고 끌 수 있게 해 줘 (기본값은 true)
- 화면 왼쪽 위(또는 비어 있는 곳)에 작은 글씨로 아래를 표시해 줘
  - 플레이어의 x, y
  - 적(또는 주요 물체)의 개수
  - 현재 gameState
  - 점수
- 6장에서 만든 showHitbox도 showDebug와 함께 켜지게 연결해 줘
- D 키를 누르면 디버그 표시가 켜지고 꺼지게 해 줘
```

켜고 플레이해 본다.

- [ ] 움직일 때 x, y가 변하는 것이 보인다
- [ ] 적이 사라지고 생길 때 개수가 변한다
- [ ] 게임 오버가 되면 `gameState`가 바뀐다
- [ ] D 키로 꺼진다

> **이 장치가 왜 중요한가.** 9장에서 난이도를 다듬고 10장에서 완성할 때, "지금 무슨 일이 벌어지는지"를 보지 못하면 추측으로 고치게 된다. **보이면 추측하지 않는다.**

### Step 4. 내 게임의 실제 버그를 고친다 (12분)

6장에서 **남겨 두라고 한 버그**를 꺼낸다. 없으면 "이상하지만 원인을 모르는 것" 또는 "바꾸고 싶은데 어디를 고칠지 모르는 것"으로 한다.

**반드시 2.8의 절차를 거친다. 기록하면서 한다.**

```
1. 현상:        (무엇이 어떻게 이상한가)
2. 에러:        (있음 / 없음. 있으면 원문)
3. 재현 조건:   (언제 생기는가)
4. 좁힌 결과:   (어느 값이 이상했는가 — console.log로 확인한 것)
5. 원인:        (내가 판단한 원인)
6. 고친 방법:   (내가 고쳤는가 / AI에게 어떻게 요청했는가)
```

**이 여섯 줄이 과제 1의 제출물이다.** 지금 적어 두면 회고를 따로 쓸 필요가 없다.

AI에게 요청할 때는 2.6의 다섯 가지를 담는다. 그리고 이 두 마디를 꼭 붙인다.

```
어느 부분이 원인인지 먼저 말해 주고, 그다음에 고쳐 줘.
다른 부분은 건드리지 마.
```

고친 뒤 **커밋한다** (`(버그 이름) 수정`).

### Step 5. 내 코드를 구역으로 나눈다 (10분)

이제 코드 전체를 정리하고 읽는다.

```
script.js를 아래 순서로 정리해 줘. 동작은 절대 바꾸지 말고, 순서와 주석만.

① 준비 (canvas, ctx)
② 상태 변수
③ 이벤트
④ 함수들
⑤ 게임 루프
⑥ 시동

각 구역 위에 ===== 로 구분선을 긋고 한국어 제목을 달아 줘.
```

정리된 코드를 위에서 아래로 훑으면서 확인한다.

- [ ] 내 게임의 **상태 변수가 몇 개**인지 센다 (적어 둔다 — 회고 재료)
- [ ] 함수가 몇 개이고, 각 **이름에서 역할을 짐작**해 본다
- [ ] 게임 루프 안의 **지우기 / 계산 / 그리기** 세 구역을 짚는다

그다음 **핵심 함수 하나를 골라** 깊게 묻는다.

```
(고른 함수 이름) 함수에 대해 세 가지를 알려 줘.
1) 이 함수가 하는 일을 한 문장으로
2) 이 함수를 지우면 게임이 어떻게 되는가
3) 이 함수에서 가장 중요한 한 줄은 무엇이고 왜 그런가
```

> 과제 2(핵심 코드 설명문)의 재료다. 받은 설명을 그대로 쓰지 않고, **읽고 이해한 뒤 내 말로** 쓴다.

### Step 6. 정리하고 커밋 (5분)

1. 실험용으로 넣은 `console.log`를 정리한다 (남겨 둘 것은 조건부로)
2. `showDebug`를 **`false`** 로 바꾼다 (코드는 지우지 않는다)
3. `debug-practice.html`은 **지우지 않고 남겨 둔다** — 제출물이다
4. 커밋 → Sync → 배포 주소에서 정상 작동 확인

## 4. 내 게임에 적용하기 (과제)

### 과제 1. 버그 해결 기록 (필수)

**두 건**을 기록한다. `my-game` 폴더에 **`디버깅기록.md`** 파일을 만든다.

- **1건:** Step 2의 숨은 버그 중 하나 (찾는 과정을 쓴다)
- **1건:** Step 4의 내 게임 실제 버그

각 건을 Step 4의 여섯 줄 양식으로 쓴다.

```markdown
# 디버깅 기록

## 버그 1 — (한 줄 제목)
1. 현상:
2. 에러:
3. 재현 조건:
4. 좁힌 결과:
5. 원인:
6. 고친 방법:

## 버그 2 — (한 줄 제목)
(같은 양식)
```

> **평가 기준은 "고쳤는가"가 아니다.** 4번(좁힌 결과)이 구체적인지를 본다. "console.log로 player.x를 찍어 보니 벽에 닿은 순간 음수가 되어 있었다" 같은 기록이 만점이다. **못 고쳤어도 좁히는 과정이 구체적이면 만점이 가능하다.**

### 과제 2. 핵심 코드 설명문 (필수)

내 게임 코드에서 **가장 중요한 함수 하나**를 골라, 설명문을 쓴다. `README.md` 아래쪽 또는 `디버깅기록.md`에 넣는다.

분량은 **10~15줄**. 아래를 포함한다.

- [ ] 이 함수가 하는 일 (한 문장)
- [ ] 코드를 **구역별로** 나눠서 설명 (3~5구역)
- [ ] 가장 중요한 한 줄을 지목하고, 왜 중요한지
- [ ] 이 함수가 없으면 게임이 어떻게 되는지
- [ ] **내 말로 썼다** — AI 설명을 복사한 것이 아니다

> **채점자가 보는 것** — AI 설명문은 문체가 균일하고 교과서적이다. 본인이 쓴 글은 "처음엔 이게 왜 필요한지 몰랐는데" 같은 흔적이 남는다. **이해한 흔적이 보이는 글**이 높은 점수를 받는다. 틀린 부분이 조금 있어도 괜찮다.

### 과제 3. 디버그 표시 장착 (필수)

- [ ] `showDebug` 변수로 켜고 끌 수 있다
- [ ] 켜면 플레이어 좌표·개수·상태·점수가 화면에 보인다
- [ ] D 키로 토글된다
- [ ] 제출 상태에서는 **꺼져 있다**

### 과제 4. 선택 과제

- 숨은 버그를 **3개 다 찾았다** (회고에 어떻게 찾았는지 쓴다)
- 친구와 서로의 `debug-practice.html`을 **교환해서** 버그를 찾아 준다
- 콘솔에 찍히는 디버그 로그를 **상황별로 정리**한다 (충돌 시에만, 상태 변경 시에만)
- 게임이 느려지는 지점이 있는지 찾아본다 (적을 50개로 늘려 보고 관찰)

### 과제 5. 회고 파일 (필수)

양식은 **부록 E**와 같다. 7주차는 아래를 포함한다.

- **1번:** 버그를 설명한 요청을 그대로 복사한다. **2.6의 다섯 가지가 들어 있는지** 스스로 확인한다
- **2번:** 막힌 점. **이번 주는 이 항목이 과제 1과 거의 같다.** 숨은 버그를 찾는 과정에서 헤맸던 부분을 쓰면 좋다
- **3번:** 코드 설명 — 과제 2를 가리키기만 해도 된다 ("디버깅기록.md의 설명문 참고")

## 이번 주 자주 막히는 지점

| 증상 | 원인과 해결 |
|---|---|
| 콘솔에 아무것도 안 나온다 | Console 탭인지 확인 / 필터가 걸려 있는지 / 페이지를 새로고침한다 |
| 에러는 있는데 줄 번호가 이상하다 | 줄 번호는 **그 줄 또는 그 위쪽**을 가리킨다. 위로 몇 줄 올려 보며 본다 |
| 에러가 너무 빠르게 수백 개 쌓인다 | 루프 안에서 에러가 나고 있다. **맨 위 첫 번째 에러**만 보면 된다 |
| `console.log`가 1초에 60줄 찍힌다 | 조건을 걸거나 키를 누를 때만 찍게 한다 |
| `console.log`를 넣었는데 안 찍힌다 | 그 줄이 실행되지 않는 곳에 있다. **그 자체가 중요한 발견이다** |
| `SyntaxError`인데 어디가 틀렸는지 모른다 | 보통 괄호·중괄호 짝. VS Code에서 괄호를 클릭하면 짝이 표시된다 |
| 고쳤는데 다른 게 망가졌다 | "다른 부분은 건드리지 마"를 안 붙였다. 2장 되돌리기로 돌아가 다시 요청 |
| AI가 코드를 전부 다시 써 버렸다 | 되돌린다. 그리고 "(함수명)만 고쳐 줘"로 범위를 좁혀 요청한다 |
| 버그가 간헐적으로만 생긴다 | 재현 조건을 더 찾는다. "특정 키를 빠르게 누를 때", "벽에 붙었을 때" 등 |
| 실험용 코드를 어디에 넣었는지 잊었다 | 소스 제어의 **diff 화면**(파일 이름 클릭)에서 바뀐 줄이 다 보인다 |

모르는 용어는 **부록 C**, 에러별 대처는 **부록 D**, 프롬프트는 **부록 B**를 본다.
