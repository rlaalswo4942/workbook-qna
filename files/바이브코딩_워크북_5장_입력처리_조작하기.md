# 5장. 조작하기: 입력 처리

> **이번 주 목표** 구경하던 화면을 **내가 조작하는 게임**으로 바꾼다. 처음으로 "플레이"가 가능해진다.

---

## 1. 학습 목표

이 장이 끝나면 다음을 할 수 있다.

- 이벤트가 무엇인지 설명할 수 있다.
- 키보드 입력을 받아서 플레이어를 움직일 수 있다.
- 조건문(`if` / `else if` / `else`)을 읽고, 간단한 것은 직접 쓸 수 있다.
- 플레이어가 화면 밖으로 나가지 않게 막을 수 있다.
- 마우스 입력을 받을 수 있다.
- **"눌린 상태를 기억하는 방식"** 과 "눌릴 때마다 움직이는 방식"의 차이를 설명할 수 있다.

---

## 2. 개념 설명

### 2.1 이벤트 — "무슨 일이 생기면 이걸 해 줘"

지금까지 코드는 **위에서 아래로 한 번 실행**되거나, **루프 안에서 계속 반복**되었다. 그런데 사용자가 키를 누르는 시점은 미리 알 수 없다.

그래서 이렇게 적어 둔다.

> **"키가 눌리면, 이 작업을 해 줘."**

이렇게 "어떤 일이 생겼을 때 실행할 작업"을 미리 등록해 두는 것이 **이벤트(event)** 처리다. 식당의 호출벨과 같다. 벨이 언제 눌릴지는 모르지만, **눌리면 직원이 온다**는 약속은 미리 되어 있다.

코드는 이런 모양이다.

```javascript
document.addEventListener("keydown", function (e) {
  // 키가 눌리면 여기가 실행된다
  console.log(e.key);
});
```

| 부분 | 뜻 |
|---|---|
| `addEventListener` | "귀를 기울여 둬" — 이벤트를 등록한다 |
| `"keydown"` | **무슨 일**을 기다리는가 → 키가 눌리는 일 |
| `function (e) {...}` | 그 일이 생기면 **실행할 작업** |
| `e` | 일어난 일에 대한 정보 묶음 (어느 키인지 등) |
| `e.key` | 눌린 키의 이름 (`"ArrowLeft"`, `"a"`, `" "` 등) |

주요 이벤트는 네 개만 알면 이 수업에서 충분하다.

| 이벤트 | 언제 생기는가 |
|---|---|
| `keydown` | 키를 **누르는 순간** |
| `keyup` | 키에서 **손을 떼는 순간** |
| `mousedown` / `click` | 마우스를 **클릭할 때** |
| `mousemove` | 마우스를 **움직일 때** |

> **`console.log()`** 는 값을 콘솔(`F12`)에 출력하는 명령이다. 7장 디버깅의 주역이지만, 이번 주부터 요긴하게 쓴다. **어떤 키가 눌렸는지 확인하는 가장 빠른 방법**이다.

### 2.2 방향키의 이름

키보드 키의 이름은 정해져 있다. 자주 쓰는 것만 보면 이렇다.

| 키 | `e.key` 값 |
|---|---|
| ← | `"ArrowLeft"` |
| → | `"ArrowRight"` |
| ↑ | `"ArrowUp"` |
| ↓ | `"ArrowDown"` |
| 스페이스바 | `" "` (공백 한 칸) |
| 엔터 | `"Enter"` |
| 알파벳 a | `"a"` (소문자) |

**대소문자를 구분한다.** `"arrowleft"`로 쓰면 작동하지 않는다. 이름이 헷갈리면 `console.log(e.key)`로 찍어 보면 바로 확인된다.

### 2.3 조건문 — 만약 ~라면

이벤트를 받으면 "어느 키인지"에 따라 다르게 행동해야 한다. 그 도구가 **조건문**이다.

```javascript
if (e.key === "ArrowLeft") {
  playerX = playerX - 5;        // 왼쪽 키면 왼쪽으로
} else if (e.key === "ArrowRight") {
  playerX = playerX + 5;        // 오른쪽 키면 오른쪽으로
} else {
  // 둘 다 아니면 아무것도 안 한다
}
```

읽는 방법은 그대로다.

```
if      (조건)  { ... }     만약 조건이 맞으면 이걸 한다
else if (조건)  { ... }     아니고 이 조건이 맞으면 이걸 한다
else            { ... }     위 어느 것도 아니면 이걸 한다
```

**`=`와 `===`를 구분해야 한다.** 이번 주에 가장 많이 나는 실수다.

| 기호 | 뜻 |
|---|---|
| `=` | **넣어라** (대입) — `x = 5`는 x에 5를 넣는다 |
| `===` | **같은가?** (비교) — `x === 5`는 x가 5인지 묻는다 |

조건 안에는 `===`를 쓴다. 비교에 쓰는 기호는 이런 것들이 있다.

| 기호 | 뜻 |
|---|---|
| `===` | 같다 |
| `!==` | 다르다 |
| `>` / `<` | 크다 / 작다 |
| `>=` / `<=` | 크거나 같다 / 작거나 같다 |
| `&&` | 그리고 |
| `\|\|` | 또는 |

### 2.4 두 가지 조작 방식 — 이번 주의 핵심

여기가 이번 주에서 가장 중요한 부분이다. 조작을 만드는 방법이 두 가지 있고, **둘의 느낌이 완전히 다르다.**

**방식 A — 이벤트에서 직접 움직인다 (초보자가 먼저 떠올리는 방식)**

```javascript
document.addEventListener("keydown", function (e) {
  if (e.key === "ArrowRight") {
    playerX = playerX + 5;      // 눌릴 때마다 5씩 이동
  }
});
```

이렇게 하면 어떻게 되는가. 직접 해 보면 금방 느낀다.

```
키를 꾹 누른다
  → 한 칸 움직인다
  → 잠깐 멈춘다 (!)
  → 그 다음에 다다다다 움직인다
```

**끊긴다.** 키보드의 "자동 반복"이 운영체제 설정에 따라 작동하기 때문이다. 또 두 키를 같이 누르면(오른쪽+위, 대각선 이동) 거의 안 된다.

**방식 B — 눌린 상태를 기억해 두고, 루프에서 움직인다 (제대로 된 방식)**

```javascript
const keys = {};                 // 눌린 키를 기억할 상자

document.addEventListener("keydown", function (e) {
  keys[e.key] = true;            // 눌렸다고 적어 둔다
});
document.addEventListener("keyup", function (e) {
  keys[e.key] = false;           // 떼었다고 적어 둔다
});

function gameLoop() {
  // ... 지우기 ...

  // 계산: 지금 눌려 있는 키를 보고 움직인다
  if (keys["ArrowLeft"])  playerX = playerX - 5;
  if (keys["ArrowRight"]) playerX = playerX + 5;

  // ... 그리기 ...
  requestAnimationFrame(gameLoop);
}
```

이 방식의 결과는 이렇다.

```
키를 꾹 누른다 → 매끄럽게 계속 움직인다
오른쪽+위를 같이 누른다 → 대각선으로 움직인다
```

**왜 이게 좋은가.** 역할이 깔끔하게 나뉘기 때문이다.

| | 역할 |
|---|---|
| 이벤트 | **기록만 한다** — "지금 오른쪽 키가 눌려 있음" |
| 게임 루프 | **움직임을 담당한다** — 매 프레임 눌린 키를 보고 계산 |

4장에서 배운 "게임은 숫자 몇 개"라는 관점과도 맞는다. `keys`는 **입력 상태**이고, 루프는 그 상태를 보고 위치를 계산한다.

> **이 수업에서는 방식 B를 쓴다.** AI가 방식 A로 만들어 주면 이렇게 요청한다.
> `"키가 눌린 상태를 keys 객체에 기록하고, 게임 루프 안에서 그 상태를 보고 움직이는 방식으로 바꿔 줘. 키를 꾹 누르면 매끄럽게 움직이고, 두 키를 동시에 누르면 대각선으로 가게."`

**`keys`는 무엇인가** — `{}`로 만든 **객체**다. 이름표가 붙은 서랍장이라고 보면 된다. `keys["ArrowLeft"]`는 "ArrowLeft라는 이름의 칸"이고, 거기에 `true`(눌림) 또는 `false`(안 눌림)를 적어 둔다. 자세한 건 몰라도 되고, **"눌린 키를 적어 두는 메모장"** 으로 이해하면 충분하다.

### 2.5 화면 밖으로 나가지 않게 막기

4장에서 본 방식을 플레이어에 적용한다.

```javascript
if (playerX < 0) playerX = 0;                                  // 왼쪽 벽
if (playerX > canvas.width - playerSize) {                     // 오른쪽 벽
  playerX = canvas.width - playerSize;
}
```

오른쪽 벽에서 `- playerSize`를 빼는 이유가 있다. 3장에서 배운 것을 떠올린다. **`fillRect(x, y, 가로, 세로)`의 x는 왼쪽 위 꼭짓점**이다. 그래서 x가 800이면 플레이어 전체가 화면 밖에 있다.

```
         x=768                x=800
           │                    │
           ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓│  ← 딱 맞게 붙는다 (800 - 32 = 768)
           │                    │
                                 ▓▓▓▓▓▓▓▓  ← x=800이면 완전히 밖으로 나간다
```

이 "크기를 빼야 한다"는 감각은 6장 충돌 판정에서 다시 중요해진다.

### 2.6 마우스 입력

마우스는 **위치를 알아내는 계산이 한 단계 더** 필요하다. 마우스 좌표는 브라우저 창 전체를 기준으로 오는데, 우리가 필요한 것은 **Canvas 안에서의 좌표**이기 때문이다.

```javascript
canvas.addEventListener("mousemove", function (e) {
  const rect = canvas.getBoundingClientRect();   // 캔버스가 화면에서 어디 있는지
  const mouseX = e.clientX - rect.left;          // 캔버스 기준 x
  const mouseY = e.clientY - rect.top;           // 캔버스 기준 y
  playerX = mouseX - playerSize / 2;   // 플레이어의 가운데가 마우스에 오게
});
```

`getBoundingClientRect()`를 빼먹으면 **마우스와 플레이어 위치가 어긋난다.** 마우스 조작에서 가장 흔한 버그이고, 원인을 모르면 한참 헤맨다.

클릭은 더 간단하다.

```javascript
canvas.addEventListener("click", function (e) {
  // 클릭했을 때 할 일
});
```

### 2.7 방향키로 화면이 스크롤되는 문제

방향키나 스페이스바를 누르면 **페이지가 위아래로 스크롤**되어 게임이 흔들리는 일이 생긴다. 브라우저의 기본 동작이기 때문이다.

막는 방법은 한 줄이다.

```javascript
document.addEventListener("keydown", function (e) {
  if (["ArrowUp", "ArrowDown", "ArrowLeft", "ArrowRight", " "].includes(e.key)) {
    e.preventDefault();      // 브라우저의 기본 동작을 막는다
  }
  keys[e.key] = true;
});
```

`e.preventDefault()`는 **"브라우저야, 네 기본 동작은 하지 마"** 라는 뜻이다. 외울 필요는 없고, **게임이 흔들릴 때 이 말을 떠올리면** 된다.

```
AI에게: "방향키와 스페이스바를 눌렀을 때 페이지가 스크롤되지 않게 preventDefault를 넣어 줘."
```

## 3. 따라 하기 실습

작업 폴더는 **`my-game`** 이다.

> **시작 전에 커밋한다.** 소스 제어 → `5장 시작 전 상태` → Commit.

### Step 1. 어떤 키가 눌렸는지 확인한다 (7분)

먼저 입력이 들어오는지부터 확인한다. AI에게 요청한다.

```
script.js 맨 아래에, 키를 누를 때마다 눌린 키 이름을
콘솔에 출력하는 코드를 추가해 줘.
```

브라우저에서 `F12` → **Console** 탭을 열어 둔 채로 방향키, 스페이스바, 알파벳을 눌러 본다.

```
ArrowLeft
ArrowRight
ArrowUp
(공백)
a
```

**키 이름이 콘솔에 찍히면 입력이 들어오고 있다는 뜻이다.** 앞으로 조작이 안 될 때 가장 먼저 확인할 것이 이것이다 — "입력이 아예 안 들어오는가, 들어오는데 움직임이 없는가".

확인했으면 이 출력 코드는 지우거나 주석 처리한다.

### Step 2. 일부러 나쁜 방식으로 만들어 본다 (10분)

**방식 A의 불편함을 몸으로 느끼는 단계다.** 이걸 겪지 않으면 왜 방식 B를 쓰는지 이해하지 못한다.

```
플레이어(파란 사각형)를 방향키로 움직이게 해 줘.
단, 일부러 아래 방식으로 만들어 줘.

- keydown 이벤트 안에서 직접 위치를 바꾸는 방식
- 눌릴 때마다 5픽셀씩 이동

(비교 실험용이야. 나중에 더 나은 방식으로 바꿀 거야.)
```

확인해 본다.

- [ ] 키를 **꾹 눌러** 본다 → 한 칸 가고 멈추다가 다다다다 움직인다
- [ ] **오른쪽+위를 동시에** 눌러 본다 → 대각선으로 안 간다
- [ ] 빠르게 **톡톡** 눌러 본다 → 이건 그럭저럭 된다

불편함을 확인했으면 메모해 둔다. **회고의 좋은 재료다.**

### Step 3. 제대로 된 방식으로 바꾼다 (12분)

이번 주의 핵심 단계다.

```
지금 방식은 키를 꾹 누르면 움직임이 끊기고, 두 키를 같이 누르면 대각선으로 안 가.
아래 방식으로 바꿔 줘.

- keys 라는 객체를 만들어서, keydown에서 true, keyup에서 false를 기록한다
- 게임 루프 안에서 keys를 보고 플레이어 위치를 계산한다
- 방향키 네 개를 모두 지원해 줘
- 방향키와 스페이스바로 페이지가 스크롤되지 않게 preventDefault를 넣어 줘
- 플레이어가 화면 밖으로 나가지 않게 네 벽에서 막아 줘
  (오른쪽/아래쪽은 플레이어 크기를 고려해서)
- 이동 속도는 변수로 코드 위쪽에 모아 줘
- 한국어 주석을 달아 줘
```

확인한다. **Step 2와 비교하는 것이 목적이다.**

- [ ] 꾹 누르면 **매끄럽게** 움직인다
- [ ] 오른쪽+위를 같이 누르면 **대각선**으로 간다
- [ ] 화면 밖으로 **나가지 않는다**
- [ ] 방향키를 눌러도 **페이지가 흔들리지 않는다**

### Step 4. 코드를 읽는다 (8분)

AI에게 묻는다.

```
방금 만든 조작 코드를 설명해 줘. 특히 이 세 가지를.
1) keys 객체가 하는 일은 무엇인가
2) 왜 keydown 안에서 직접 움직이지 않고, 게임 루프에서 움직이는가
3) 오른쪽 벽을 막을 때 왜 플레이어 크기를 빼는가
```

읽고 나서 직접 짚어 본다.

- [ ] `keys`에 기록하는 두 곳 (`keydown`, `keyup`)
- [ ] 루프 안에서 `keys`를 읽는 곳 (`if (keys[...])`)
- [ ] 벽을 막는 네 줄
- [ ] 이동 속도 변수

### Step 5. 직접 손으로 조정한다 (8분)

**AI 없이** 고친다.

1. **이동 속도**를 바꿔 본다 (3 → 10 → 1). 내 게임에 맞는 값을 찾는다
2. **방향을 반대로** 만들어 본다 — 왼쪽 키의 `-`를 `+`로 바꾸면? → 조작이 뒤집힌다. 확인하고 되돌린다
3. **위아래 조작을 막아** 본다 — `ArrowUp` / `ArrowDown` 줄을 주석 처리한다. 좌우만 움직이는 게임이면 이게 맞는 설정이다

> 2번 실험이 중요하다. **`+`와 `-` 하나가 조작 방향을 결정한다**는 것을 보면, 7장에서 "조작이 반대로 돼요" 같은 버그를 스스로 고칠 수 있다.

### Step 6. 내 게임의 조작을 완성한다 (10분)

기획서 3번에 정한 조작으로 맞춘다. 게임에 따라 필요한 것이 다르다.

**좌우만 움직이는 게임이라면**
```
위아래 조작은 빼고, 좌우만 움직이게 정리해 줘.
```

**마우스로 조작하는 게임이라면**
```
플레이어가 마우스의 x 좌표를 따라가게 바꿔 줘.
getBoundingClientRect를 써서 캔버스 기준 좌표로 변환해 줘.
플레이어는 마우스 위치의 가운데에 오게 해 줘.
```

**클릭으로 무언가 하는 게임이라면**
```
캔버스를 클릭하면 클릭한 위치에 작은 원이 하나 생기게 해 줘.
(원의 위치를 변수에 저장하고, 게임 루프에서 그리는 방식으로)
```

**스페이스바로 점프하는 게임이라면**
```
스페이스바를 누르면 플레이어가 위로 뛰어오르고,
중력으로 다시 바닥에 내려오게 해 줘.

- 위로 솟는 속도는 음수로 (Canvas에서 위는 y가 작아지는 방향)
- 매 프레임 세로 속도에 중력 값을 더해 준다
- 바닥에 닿으면 멈추고, 다시 점프할 수 있게
- 공중에서는 다시 점프할 수 없게
- 중력과 점프력은 변수로 위쪽에 모아 줘
```

> **점프를 고른 사람에게** — 중력은 "매 프레임 세로 속도에 조금씩 더하는 값"이다(보통 0.5~1). 처음에는 점프가 달 위처럼 느리거나 돌처럼 뚝 떨어진다. **점프력과 중력 두 숫자를 번갈아 조정**하면서 느낌을 찾는다. 이게 4장에서 말한 튜닝이다.

### Step 7. 커밋하고 배포 (5분)

1. 소스 제어 → `방향키 조작 구현, 화면 경계 처리` → **Commit**
2. **Sync Changes**
3. 배포 주소에서 **직접 플레이해 본다**

**친구에게 링크를 보내 본다.** 아직 게임이라고 하기엔 이르지만, 남이 조작할 수 있는 것을 만든 건 이번 주가 처음이다.

### 과제 3. 방식 A와 방식 B 비교 (필수)

- 방식 B에서 그게 어떻게 해결되었는가
- 왜 그런 차이가 생기는가 (내 이해대로)

### 과제 4. 선택 과제 (하나 이상 권장)

- 스페이스바로 **발사**되는 무언가를 만든다 (6장 충돌의 예습)

## 이번 주 자주 막히는 지점

| 증상 | 원인과 해결 |
|---|---|
| 키를 눌러도 아무 일이 없다 | Step 1처럼 `console.log(e.key)`로 **입력이 들어오는지** 먼저 확인 |
| 키 이름이 콘솔에 찍히는데 안 움직인다 | 키 이름 대소문자 확인 (`"ArrowLeft"`). `keys[...]`를 루프에서 읽는지 확인 |
| 키 이벤트를 걸었는데 전혀 안 먹는다 | 이벤트를 `canvas`에 걸었다. canvas는 기본적으로 키 입력을 받지 않는다. **키보드는 `document`에 건다** |
| 꾹 누르면 끊긴다 | 방식 A다. 방식 B(`keys` 객체)로 바꾼다 |
| 두 키를 같이 누르면 한 방향만 된다 | 같은 원인. 방식 B로 바꾼다 |
| 방향키를 누르면 페이지가 흔들린다 | `e.preventDefault()`가 없다 |
| 플레이어가 벽을 반쯤 넘어가서 멈춘다 | 오른쪽/아래 경계에서 **플레이어 크기를 빼지 않았다** |
| 벽에서 덜덜 떨린다 | 위치 보정과 속도 처리가 충돌한다. "벽에 닿으면 위치를 벽 안쪽으로 고정해 줘"로 요청 |
| 마우스와 플레이어 위치가 어긋난다 | `getBoundingClientRect()`를 쓰지 않았다 |
| 점프가 공중에서 무한히 된다 | "바닥에 있을 때만 점프할 수 있게 해 줘"로 요청 |
| 점프가 너무 느리거나 뚝 떨어진다 | 중력과 점프력 숫자 튜닝. 중력 0.5~1, 점프력 -10~-15 근처에서 시작 |
| 조작을 넣었더니 4장 움직임이 멈췄다 | 루프가 두 개 생겼거나 루프 구조가 깨졌다. 2장 되돌리기로 돌아가 다시 요청 |

모르는 용어는 **부록 C**, 환경 문제는 **부록 D**, 상황별 프롬프트는 **부록 B**를 본다.
