# 0장. 들어가며

> 이 장은 수업 첫 주 앞머리 15분 또는 사전 읽기 자료로 쓴다. 실습은 1장부터 시작한다.

## 학습 목표

이 장을 읽고 나면 다음을 말할 수 있다.

- 바이브 코딩이 무엇이고, 무엇이 아닌지 구분할 수 있다.
- 이 워크북이 10주 동안 나를 어디로 데려가는지 설명할 수 있다.
- AI와 함께 코드를 쓸 때 내가 책임져야 하는 것이 무엇인지 안다.

---

## 1. 바이브 코딩이란 무엇인가

### 코드를 "타이핑"하지 않고 만드는 시대

예전에 프로그램을 만든다는 것은 문법을 외우고, 한 글자씩 직접 타이핑하고, 세미콜론 하나가 빠져서 몇 시간을 헤매는 일이었다. 그래서 "프로그래밍을 배운다"는 말은 사실상 "문법을 외운다"는 말과 비슷했다.

지금은 다르다. 우리는 **만들고 싶은 것을 말로 설명하고, AI가 코드를 쓰고, 그 결과를 내가 확인하고 고쳐 나가는 방식**으로 프로그램을 만들 수 있다. 이런 방식을 **바이브 코딩(vibe coding)** 이라고 부른다.

예를 들어 이런 식이다.

> **나:** 화면 가운데에 빨간 공을 하나 그리고, 방향키로 움직이게 해 줘.
>
> **AI:** (코드를 작성해서 파일에 직접 써 준다)
>
> **나:** (브라우저에서 확인) 움직이긴 하는데 화면 밖으로 나가 버려. 화면 끝에서는 더 못 가게 막아 줘.
>
> **AI:** (코드를 수정한다)

이 대화가 코딩이다. 여기서 중요한 것은 문법 지식이 아니라 **내가 무엇을 원하는지 정확히 말하는 능력**, 그리고 **결과가 내 의도와 맞는지 판단하는 능력**이다.

### 그러면 아무것도 안 배워도 되는가

아니다. 이것이 이 워크북의 가장 중요한 전제다.

바이브 코딩은 **타이핑을 대신해 주는 것이지, 이해를 대신해 주는 것이 아니다.** 실제로 해 보면 금방 벽을 만난다.

- "이상하게 동작해요"라고만 말하면 AI는 엉뚱한 곳을 고친다. → 무엇이 어떻게 이상한지 말할 수 있어야 한다.
- 코드가 400줄이 넘어가면 AI가 멀쩡한 부분을 망가뜨린다. → 어디를 고쳐야 하는지 짚어 줄 수 있어야 한다.
- 에러 메시지가 떴는데 어디를 봐야 할지 모른다. → 브라우저 콘솔을 열고 읽을 수 있어야 한다.
- 다 만들었는데 내가 왜 이렇게 만들었는지 설명하지 못한다. → 그건 내 작품이 아니다.

그래서 이 수업은 **문법 암기는 최소한으로, 개념 이해와 판단력은 제대로** 가는 방향으로 설계되어 있다. 변수가 무엇인지, 게임 루프가 왜 필요한지, 충돌 판정이 어떤 계산인지는 안다. 대신 그것을 쓰는 코드를 한 글자씩 외우지는 않는다.

### 바이브 코딩이 아닌 것

| 바이브 코딩 | 바이브 코딩이 아닌 것 |
|---|---|
| AI가 쓴 코드를 읽고 판단한다 | AI가 준 코드를 보지 않고 붙여넣는다 |
| 원하는 결과를 구체적으로 설명한다 | "알아서 멋있게 만들어 줘"로 끝낸다 |
| 작동을 확인하고 다음 단계로 간다 | 작동하는지 모른 채 계속 쌓는다 |
| 막히면 무엇이 막혔는지 특정한다 | 막히면 처음부터 다시 만든다 |

마지막 줄이 특히 중요하다. 비전공자가 바이브 코딩에서 가장 많이 실패하는 지점은 **"고치는 것보다 새로 만드는 게 빠를 것 같다"는 유혹에 빠져 매주 처음부터 다시 시작하는 것**이다. 이 워크북의 과제가 누적 구조인 이유가 여기에 있다.

## 2. 이 워크북 사용법

### 우리가 도착할 곳

10주 뒤 여러분은 이것을 갖게 된다.

- **인터넷 주소가 있는, 내가 만든 웹 게임.** 친구에게 링크를 보내면 바로 플레이할 수 있다.
- **내 GitHub 저장소.** 매주 무엇을 어떻게 만들었는지가 기록으로 남는다.
- **내 말로 설명할 수 있는 코드.** 적어도 핵심 부분은 그렇다.

게임의 종류는 자유다. 피하기, 맞추기, 퍼즐, 리듬, 클릭 게임, 텍스트 게임 — 무엇이든 좋다. 단, **브라우저에서 돌아가는 2D 게임**이라는 조건은 지킨다. 3D나 모바일 앱은 이 수업의 범위가 아니다.

### 매주 흐름

| 비중 | 무엇을 하는가 |
|---|---|
| 설명 30% | 이번 주의 개념. "왜 이게 필요한가"를 이해한다 |
| 실습 40% | 수업 시간에 같이 따라 만든다. 작은 예제 하나를 끝까지 완성한다 |
| 과제 30% | 그 개념을 **내 게임에** 적용한다 |

주차마다 비중은 조금씩 달라진다. 개념이 많은 주는 설명이 늘고, 다듬는 주는 실습이 늘어난다.

### 각 장의 구성

모든 장이 같은 다섯 단계로 되어 있다.

1. **학습 목표** — 이 장이 끝나면 할 수 있어야 하는 것
2. **개념 설명** — 알아야 하는 것. 코드보다 그림과 비유가 많다
3. **따라 하기 실습** — 같이 만들어 보는 작은 예제
4. **내 게임에 적용하기** — 과제. 같은 개념을 내 게임에 넣는다
5. **제출 체크리스트** — 제출 전에 확인할 것들

### 과제는 누적된다 (중요)

이 수업의 과제는 **매주 다른 것을 만드는 게 아니라, 하나의 게임을 열 번에 걸쳐 쌓아 올리는 것**이다.

```
3장: 게임 화면이 그려진다
  ↓
4장: 거기에 있는 물체가 움직인다
  ↓
5장: 그 물체를 내가 조작할 수 있다
  ↓
6장: 점수가 오르고 게임 오버가 된다  ← 여기서 플레이 가능한 게임이 된다
  ↓
8장: 소리가 나고 최고 점수가 저장된다
  ↓
10장: 완성해서 배포하고 발표한다
```

그래서 **한 주를 건너뛰면 다음 주가 막힌다.** 반대로 매주 조금씩만 쌓으면 10주 뒤에 꽤 그럴듯한 것이 나와 있다.

### 제출물은 두 가지다

매주 제출하는 것은 **결과물**과 **과정 증거**다.

- **결과물** — GitHub 저장소 링크 (2장 이후로는 플레이 가능한 배포 링크까지)
- **과정 증거** — 저장소 안의 회고 파일. 고정 양식으로 다음 세 가지를 쓴다.
  1. **이번 주에 쓴 핵심 프롬프트** — AI에게 뭐라고 말했는지. 그대로 복사해 온다
  2. **막힌 점과 해결 방법** — 무엇이 안 됐고, 어떻게 뚫었는지
  3. **코드 한 부분을 내 말로 설명** — 이번에 추가된 코드 중 한 조각을 골라, 왜 이게 필요하고 무슨 일을 하는지 설명한다

과정 증거를 요구하는 이유는 명확하다. **결과물만으로는 여러분이 무엇을 배웠는지 알 수 없기 때문이다.** 잘 돌아가는 게임보다, 막혔던 지점을 스스로 뚫어 본 기록이 더 중요하다. 그래서 "실패했지만 왜 실패했는지 아는" 주차는 좋은 평가를 받을 수 있고, "잘 돌아가지만 왜 돌아가는지 모르는" 주차는 그렇지 않다.

자세한 양식과 평가 기준은 **부록 E**에 있다.

### 준비물

| 항목 | 설명 |
|---|---|
| Windows 노트북 | 수업 시간에 가져온다 |
| VS Code | 무료. 1장에서 같이 설치한다 |
| 생성형 AI 구독 | **에이전트 모드가 되는 것** — 아래 조건 참고 |
| GitHub 계정 | 무료. 2장에서 만든다 |
| 웹 브라우저 | Chrome 또는 Edge |

**AI 도구 조건** — 이 수업에서 쓰는 AI는 **에디터 안에서 파일을 직접 고칠 수 있어야 한다.** 흔히 "에이전트 모드"라고 부른다. 채팅창에서 코드를 받아 손으로 복사·붙여넣는 방식으로는 이 수업을 따라오기 매우 힘들다.

어떤 도구를 쓰든 상관없다. VS Code에 붙이는 방식, Cursor 같은 별도 에디터를 쓰는 방식 모두 괜찮다. **도구별 설치와 연결 방법은 부록 A**에 정리해 두었다. 본문은 특정 도구에 의존하지 않고 쓰여 있으니, 본문의 프롬프트는 어떤 도구에서든 그대로 쓸 수 있다.

Node.js나 복잡한 빌드 도구는 쓰지 않는다. **순수 HTML/CSS/JavaScript와 Live Server**만으로 끝까지 간다.

### 막혔을 때 가는 곳

| 상황 | 가는 곳 |
|---|---|
| 뭐라고 물어봐야 할지 모를 때 | 부록 B — 상황별 프롬프트 모음 |
| 모르는 단어가 나왔을 때 | 부록 C — 용어집 |
| Windows에서 뭔가 안 될 때 | 부록 D — 문제 해결 FAQ |
| 제출 양식이 헷갈릴 때 | 부록 E — 제출 양식과 평가 루브릭 |
| 그래도 안 될 때 | 담당 교수 / 수업 게시판 |

## 3. AI와 일하는 원칙

이 수업에서 AI 사용은 **권장이 아니라 전제**다. 쓰지 말라고 하지 않는다. 대신 지켜야 하는 선이 세 개 있다.

### 원칙 1. 내가 제출한 코드는 내 책임이다

AI가 썼더라도, 제출한 순간부터 그 코드는 여러분의 것이다. 따라서 다음 질문에 답할 수 있어야 한다.

- 이 부분은 무슨 일을 하는가?
- 왜 이렇게 했는가? 다른 방법은 없었는가?
- 여기를 지우면 무엇이 깨지는가?

답할 수 없는 코드가 섞여 있다면, 그건 "일단 돌아가니까 넘어간" 코드다. 그 상태로 쌓으면 **나중에 반드시 터진다.** 7장에서 코드 읽는 법을 따로 다루는 이유가 이것이다.

실전 습관 하나: **AI가 코드를 준 뒤에 "이 코드가 하는 일을 한 줄씩 설명해 줘"라고 한 번 더 물어보는 것.** 이 한 번이 모든 것을 바꾼다. 매주 회고에 "코드 한 부분 설명"을 쓰게 하는 것도 이 습관을 들이기 위한 장치다.

### 원칙 2. 비밀은 코드에 쓰지 않는다

GitHub에 올린 코드는 **전 세계가 볼 수 있다.** 다음은 절대 코드 파일에 쓰지 않는다.

- API 키, 비밀번호, 토큰 같은 인증 정보
- 본인이나 타인의 전화번호, 주소, 학번 등 개인정보
- 다른 사람의 사진이나 작업물을 허락 없이

본과정(1~10장)에서는 API 키를 쓸 일이 없으니 당장 걱정할 것은 없다. 다만 심화 11장에서 온라인 랭킹을 만들면 바로 이 문제가 생긴다. 그때 제대로 다룬다.

하나 더: **AI 도구의 채팅창에 민감한 정보를 붙여넣는 것도 조심한다.** 에러 메시지를 복사할 때 개인정보가 함께 묻어 들어가는 일이 흔하다.

### 원칙 3. AI 사용은 숨기지 않고 기록한다

이 수업에서 **AI를 썼다는 사실은 감점 사유가 아니다. 숨기는 것이 문제다.**

허용되는 것과 안 되는 것을 분명히 해 두자.

| 괜찮다 | 안 된다 |
|---|---|
| AI에게 코드를 쓰게 한다 | 다른 학생의 저장소를 그대로 복사한다 |
| AI에게 에러를 고치게 한다 | 남이 만든 게임을 자기 것이라고 제출한다 |
| AI에게 개념을 설명받는다 | 회고 파일을 AI에게 통째로 쓰게 한다 |
| 인터넷의 예제를 참고한다 | 출처 없이 남의 에셋(그림·음악)을 쓴다 |

세 번째 줄을 특히 주의하자. **회고 파일은 여러분이 직접 쓴다.** 그것이 평가의 핵심이기 때문이다. 코드는 AI와 같이 쓰고, 회고는 혼자 쓴다. 이게 이 수업의 규칙이다.

에셋 저작권은 8장에서 무료 소재 구하는 법과 함께 다룬다.

## 4. 시작하기 전에 — 마음가짐 하나

프로그래밍을 처음 하는 사람들이 가장 많이 하는 오해가 있다. **"코딩 잘하는 사람은 막히지 않는다"**는 것이다.

사실은 반대다. 코딩은 막히는 일이 대부분이고, 잘하는 사람은 **막혔을 때 빠져나오는 데 익숙한 사람**이다. 10주 동안 여러분은 수십 번 막힐 것이다. 그건 잘못하고 있다는 신호가 아니라, 제대로 하고 있다는 신호다.

그래서 이 수업의 성공 기준은 "에러 없이 매끄럽게"가 아니다. **막혔다 → 무엇이 막혔는지 특정했다 → 뚫었다 → 기록했다.** 이 사이클을 열 번 돌리는 것이다.

이제 1장에서 환경을 만들고, 첫 웹페이지를 띄워 보자.
