# 9장. 다듬기: 플레이테스트와 개선

> **이번 주 목표** 새 기능을 **넣지 않는다.** 남이 플레이하는 것을 보고 고친다.

---

## 1. 학습 목표

이 장이 끝나면 다음을 할 수 있다.

- 플레이테스트를 올바른 방법으로 진행할 수 있다 (설명하지 않고 관찰한다).
- 피드백에서 **증상과 처방을 구분**할 수 있다.
- 고칠 것의 우선순위를 정할 수 있다.
- AI에게 코드 정리(리팩터링)를 안전하게 맡길 수 있다.
- 휴대폰에서도 플레이할 수 있게 만들 수 있다.

---

## 2. 개념 설명

### 2.1 이번 주에는 새 기능을 넣지 않는다

8장까지 매주 뭔가를 추가했다. 이번 주는 다르다.

> **9장의 원칙: 기능 추가 금지. 다듬기만 한다.**

이유는 두 가지다.

**첫째, 지금 내 게임은 "나한테만 재미있는 게임"일 가능성이 높다.** 7주 동안 내가 만들고 내가 테스트했기 때문에, 나는 조작에 익숙하고 규칙을 다 알고 있다. 처음 보는 사람에게는 전혀 다른 경험이다.

**둘째, 10장은 완성과 발표 주차다.** 거기서 새 기능을 넣기 시작하면 발표 직전에 게임이 깨진다. **이번 주가 사실상 마지막 수정 기회**라고 보는 게 안전하다.

그래서 이번 주의 작업은 세 가지다.

| 작업 | 목적 |
|---|---|
| 플레이테스트 | 남의 눈으로 내 게임을 본다 |
| 피드백 반영 | 가장 큰 문제부터 고친다 |
| 정리(리팩터링)와 모바일 | 발표와 제출에 대비한다 |

### 2.2 플레이테스트의 규칙 — 입을 닫는다

플레이테스트에서 초보자가 가장 많이 하는 실수는 **설명하는 것**이다.

```
❌ "이거 방향키로 움직이는 거야. 저 빨간 거 피해야 해. 아, 그거 누르면 안 되고..."
```

이렇게 하면 **얻을 정보가 사라진다.** 플레이테스트의 목적은 "내 게임이 설명 없이 이해되는가"를 확인하는 것인데, 설명해 버리면 그 질문에 답할 수 없다.

**네 가지 규칙**

| 규칙 | 이유 |
|---|---|
| **① 설명하지 않는다** | 링크만 받은 사람과 같은 조건을 만든다 |
| **② 중간에 말 걸지 않는다** | 막히는 지점이 어디인지 봐야 한다 |
| **③ 변명하지 않는다** | "그건 아직 안 만든 거야"는 정보를 버리는 말이다 |
| **④ 본다** | 말보다 **행동**이 정확하다 |

③번이 특히 어렵다. 내가 만든 것을 남이 못 하는 것을 보면 변명하고 싶어진다. 하지만 **그 순간이 가장 중요한 정보**다. 꾹 참고 메모한다.

**30초 규칙**

> **처음 30초 안에 무엇을 해야 하는지 모르면, 그 게임은 실패한다.**

링크를 받은 사람은 설명서를 읽지 않는다. 30초 안에 "아, 이걸 피하는 거구나"를 알아야 한다. 8장에서 시작 화면에 조작법을 넣은 이유가 이것이다.

**관찰할 것 — 말이 아니라 행동**

| 관찰 항목 | 드러나는 문제 |
|---|---|
| 시작 화면에서 몇 초 머뭇거렸나 | 시작 방법이 안 보인다 |
| 처음 어떤 키를 눌러 봤나 | 조작이 직관적이지 않다 |
| 몇 초에 처음 죽었나 | 난이도 시작점이 너무 높다 |
| 죽고 나서 **다시 했나** | 재시작 방법이 안 보이거나, 재미가 없다 |
| 몇 판 했나 | 가장 솔직한 재미 지표다 |
| 어디서 웃거나 아쉬워했나 | 잘 만든 부분이다. **지켜야 한다** |
| 점수가 내 기록과 얼마나 다른가 | 난이도 체감 차이 |

**마지막 항목을 꼭 비교한다.** 내가 80점을 내는 게임에서 처음 하는 사람이 5점을 낸다면, 그건 "어려운 게임"이 아니라 **"나만 할 수 있는 게임"** 이다.

**끝난 뒤에 묻는 세 가지**

플레이 중에는 묻지 않고, 끝난 뒤에 묻는다.

1. **"무슨 게임인 것 같았어?"** → 의도가 전달됐는지
2. **"어디가 제일 답답했어?"** → 가장 큰 문제
3. **"한 판 더 하고 싶어?" (이유도)** → 재미의 핵심

> "재미있었어?"는 묻지 않는다. **거의 모두 "재미있었어"라고 대답한다.** 친구는 친절하기 때문이다. 위의 세 질문은 친절하게 대답해도 정보가 남는다.

### 2.3 피드백 해석 — 증상과 처방을 구분한다

플레이테스터가 하는 말은 대개 **처방 형태**로 온다. 그런데 그 처방이 정답인 경우는 드물다.

```
테스터의 말:  "플레이어가 더 빨라야 해"      ← 처방
실제 증상:    "피하고 싶은데 못 피했다"       ← 증상
진짜 원인:    적이 너무 많아서 피할 틈이 없다  ← 원인
```

이 경우 플레이어 속도를 올리면 조작이 미끄러워져서 더 나빠질 수도 있다. **고쳐야 할 것은 적의 개수**다.

| 테스터의 말 (처방) | 가능한 증상 | 의심할 원인 |
|---|---|---|
| "점프를 더 높게" | 넘어야 할 것을 못 넘었다 | 장애물 높이, 점프력, 중력 |
| "속도를 빠르게" | 피할 수 없었다 | 적의 개수·속도, 판정 영역 |
| "너무 어려워" | 10초 만에 죽었다 | 시작 난이도, 난이도 상승 속도 |
| "뭘 해야 할지 몰랐어" | 시작 화면을 지나쳤다 | 조작법 표시, 글씨 크기 |
| "지루해" | 30초 넘게 아무 일도 없었다 | 난이도가 안 올라간다, 보상이 없다 |
| "갑자기 죽었어" | 억울하게 느꼈다 | **판정 영역이 그림보다 크다** (6장) |

**"갑자기 죽었어"는 특히 중요한 신호다.** 거의 항상 히트박스 문제다. `showHitbox`를 켜서 확인한다 — 6장에서 만들고 7장에서 디버그 표시에 연결해 둔 장치가 여기서 쓰인다.

**해석 순서**

```
1. 들은 말을 그대로 적는다 (처방)
2. "그 사람이 무엇을 하려다 실패했나"를 적는다 (증상)
3. 내 코드에서 어느 숫자가 그 증상을 만드는지 찾는다 (원인)
4. 그 숫자를 고친다
```

4장부터 쌓은 "게임은 숫자 몇 개다"라는 관점이 여기서 정점에 달한다. **대부분의 피드백은 코드를 바꾸지 않고 숫자만 바꿔서 해결된다.**

### 2.4 우선순위 — 전부 고칠 수 없다

1.5시간에 모든 피드백을 반영할 수는 없다. 세 기준으로 고른다.

| 기준 | 질문 |
|---|---|
| **빈도** | 두 명 이상이 같은 걸 겪었나? → 최우선 |
| **치명도** | 게임을 못 하게 만드는 문제인가? |
| **비용** | 숫자 하나로 해결되나, 구조를 바꿔야 하나? |

실전 순서는 이렇다.

```
1순위: 여러 명이 겪은 + 치명적 + 숫자로 해결  ← 반드시 고친다
2순위: 여러 명이 겪은 + 치명적 + 구조 변경     ← 가능하면 고친다
3순위: 한 명 의견 + 숫자로 해결                ← 시간이 남으면
4순위: 한 명의 취향 + 구조 변경                ← 고치지 않는다. 기록만 한다
```

**4순위를 고치지 않는 것도 판단이다.** 회고에 "이 피드백은 받았지만 반영하지 않았다, 이유는 ○○"이라고 쓰면 그것도 좋은 평가를 받는다. **모든 의견을 다 따르는 것은 설계가 아니다.**

### 2.5 리팩터링 — 동작을 바꾸지 않고 정리한다

**리팩터링(refactoring)은 "겉보기 동작은 그대로 두고 코드 내부만 정리하는 것"** 이다.

지금 `script.js`는 200~300줄쯤 되었을 것이다. 정리하면 두 가지 이득이 있다.

- 10장에서 설명하고 발표하기가 쉬워진다
- AI가 엉뚱한 곳을 고치는 일이 줄어든다

**그런데 리팩터링은 위험하다.** "정리만 했다"면서 동작이 바뀌는 일이 흔하다. 그래서 규칙이 있다.

> **리팩터링 4원칙**
> 1. **반드시 먼저 커밋한다** (되돌릴 지점)
> 2. **한 번에 하나만** 요청한다
> 3. **"동작은 절대 바꾸지 마"** 를 명시한다
> 4. **매번 플레이해서 확인한다**

**테스트 체크리스트를 만들어 둔다**

리팩터링 후에 매번 확인할 목록이다. 종이에 적거나 메모장에 두고, **하나씩 눌러 본다.**

```
[ ] 시작 화면이 뜬다
[ ] 키를 누르면 시작된다
[ ] 조작이 된다 (모든 방향)
[ ] 벽에서 막힌다
[ ] 적이 움직인다
[ ] 부딪히면 게임 오버
[ ] 점수가 오른다
[ ] 소리가 난다 / 음소거가 된다
[ ] 최고 점수가 저장된다
[ ] R키 재시작이 된다
[ ] 재시작 후 점수·난이도가 초기화된다
[ ] 콘솔에 에러가 없다
```

**이 목록이 10장 최종 점검에도 그대로 쓰인다.** 지금 만들어 두면 다음 주가 편하다.

**안전한 리팩터링 요청의 예**

```
script.js를 정리해 줘. 동작은 절대 바꾸지 마.

이번에는 이것만:
- 게임 루프 안의 그리기 부분을 draw() 함수로 분리해 줘
- 다른 것은 건드리지 마
```

**위험한 요청** — 이렇게 하면 게임이 바뀐다.

```
❌ "코드를 깔끔하게 정리해 줘"            → 뭘 할지 모른다. 멋대로 바꾼다
❌ "최적화해 줘"                          → 동작이 바뀔 수 있다
❌ "더 좋은 구조로 리팩터링해 줘"          → 클래스나 모듈을 도입해 버린다
```

마지막 것이 특히 위험하다. **내가 이해하지 못하는 구조로 바뀌면 10장에서 설명할 수 없다.** 이 수업의 평가 기준에 정면으로 어긋난다.

### 2.6 모바일 대응 — 어디까지 할 것인가

친구에게 링크를 보내면 대부분 **휴대폰으로 먼저 열어 본다.** 그런데 지금 내 게임은 아마 이런 상태다.

- 화면이 작아서 canvas가 잘린다
- 방향키가 없어서 조작을 아예 못 한다

**완전한 모바일 대응은 이 수업의 범위가 아니다.** 하지만 두 단계로 나눠서, 할 수 있는 만큼 한다.

**1단계: 화면에 맞게 보이기 (필수, 쉽다)**

`index.html`에 한 줄, CSS에 몇 줄로 해결된다.

```html
<meta name="viewport" content="width=device-width, initial-scale=1.0">
```

이 줄이 없으면 휴대폰이 페이지를 **축소해서** 보여 준다. 글씨가 깨알같이 작아진다.

그리고 canvas가 화면 폭을 넘지 않게 한다.

```css
canvas {
  max-width: 100%;
  height: auto;
}
```

> **주의: CSS로 canvas 크기를 바꾸면 그림이 늘어난다.** 3장에서 본 문제다. 좌표 계산은 `width="800"`을 그대로 쓰고, 보이는 크기만 CSS로 줄이는 것이다. 마우스·터치 좌표를 쓰는 게임은 **이 비율 차이 때문에 위치가 어긋난다** — `getBoundingClientRect`의 크기와 canvas 크기의 비율로 보정해야 한다. AI에게 요청할 때 이 점을 명시한다.

**2단계: 터치로 조작하기 (선택)**

조작 방식에 따라 난이도가 다르다.

| 내 게임의 조작 | 모바일 대응 난이도 |
|---|---|
| 마우스 따라가기 | **쉽다** — `touchmove`를 추가하면 거의 끝 |
| 클릭 | **쉽다** — `touchstart` 추가 |
| 스페이스바 점프 | **보통** — 화면 아무 곳이나 탭하면 점프 |
| 좌우 방향키 | **보통** — 화면 좌/우 절반을 탭하거나, 화면에 버튼을 그린다 |
| 네 방향 + 복합 조작 | **어렵다** — 이 수업에서는 권하지 않는다 |

터치 이벤트는 키보드와 비슷하다.

| 터치 | 대응하는 마우스 |
|---|---|
| `touchstart` | `mousedown` |
| `touchmove` | `mousemove` |
| `touchend` | `mouseup` |

한 가지 주의할 점이 있다. **터치할 때 화면이 스크롤되거나 확대되는 것**을 막아야 한다. 5장의 `preventDefault`와 같은 문제다.

**할 수 없다면 그렇게 적는다**

네 방향 조작처럼 모바일에서 어려운 게임이라면, **시작 화면에 한 줄 적는 것**이 정직한 해결이다.

```
"PC에서 방향키로 플레이해 주세요"
```

`README.md`에도 적는다. **못 하는 것을 숨기지 않고 적는 것**도 평가 대상이다.

## 3. 따라 하기 실습

작업 폴더는 **`my-game`** 이다.

> **시작 전에 커밋한다.** 소스 제어 → `9장 시작 전 상태` → Commit. **이번 주는 리팩터링을 하므로 커밋이 특히 중요하다.**

### Step 1. 서로 플레이테스트 (20분) — 이번 주 핵심

수업 시간에 **짝을 바꿔 가며** 한다. 2인 1조로 10분씩 교대한다.

**테스터 역할 (내가 남의 게임을 할 때)**

- 배포 링크만 받는다. **설명을 듣지 않는다**
- 생각나는 것을 **소리 내어 말한다** ("이게 뭐지?", "아 피하는 거구나", "왜 죽었지?")
- 최소 **3판** 한다
- 끝나면 2.2의 세 가지 질문에 답해 준다

**제작자 역할 (남이 내 게임을 할 때)**

**입을 닫는다.** 그리고 아래 양식에 **적는다.** 양식은 **부록 E.6**에 있다.

```markdown
## 플레이테스트 기록 — (테스터 이름/구분)

- 설명 없이 시작했을 때 처음 누른 키:
- 시작하기까지 걸린 시간:
- 처음 죽기까지 걸린 시간:
- 플레이한 판 수:
- 테스터 점수 / 내 최고 기록:
- 테스터가 소리 내어 말한 것 (그대로):
  -
  -
- 멈칫한 지점:
- 웃거나 좋아한 지점:

### 끝난 뒤 질문
1. 무슨 게임인 것 같았나:
2. 어디가 가장 답답했나:
3. 한 판 더 하고 싶은가 / 이유:
```

**두 명 이상에게 받는다.** 한 명은 **게임을 처음 보는 사람**이어야 한다 (수업 외에서 받아 온 것도 인정).

### Step 2. 피드백을 정리하고 우선순위를 정한다 (10분)

받은 기록을 표로 옮긴다. **2.3의 해석 순서**를 따른다.

```markdown
| 들은 말 (처방) | 실제 증상 | 의심 원인 | 빈도 | 우선순위 | 반영 여부 |
|---|---|---|---|---|---|
| "더 빨라야 해" | 피하려는데 못 피했다 | 적 개수가 많다 | 2명 | 1 | 반영 |
| "갑자기 죽었어" | 안 닿은 것 같은데 죽었다 | 히트박스가 크다 | 2명 | 1 | 반영 |
| "뭘 해야 할지 몰랐어" | 시작 화면을 지나쳤다 | 조작법 글씨가 작다 | 1명 | 2 | 반영 |
| "보스가 있으면 좋겠어" | (취향) | - | 1명 | 4 | 미반영 — 범위 초과 |
```

**1순위 2~3개만 고른다.** 나머지는 기록만 하고 넘어간다.

### Step 3. 1순위를 고친다 (12분)

**숫자로 해결되는 것부터 한다.** 대부분은 AI 없이 내가 직접 고칠 수 있다.

- 적 개수·속도 → 변수 숫자를 바꾼다
- 난이도 시작점 → 시작 속도를 낮춘다
- 히트박스 → `showHitbox`를 켜서 확인하고, 판정 영역을 줄인다
- 글씨 크기 → `ctx.font`의 숫자를 키운다

**고칠 때마다 플레이해서 확인한다.** 한꺼번에 세 개를 바꾸면 무엇이 효과가 있었는지 모른다.

코드 구조를 바꿔야 하는 것만 AI에게 요청한다. 이때도 범위를 좁힌다.

```
(현상)을 고치고 싶어. (어느 함수 / 어느 부분)만 고쳐 줘.
다른 부분은 건드리지 마.
```

고친 뒤 **커밋한다** (`플레이테스트 피드백 반영`).

### Step 4. 테스트 체크리스트를 만든다 (5분)

2.5의 목록을 내 게임에 맞게 고쳐서 **`테스트목록.md`** 파일로 만든다.

- 내 게임에 없는 항목은 지운다
- 내 게임에만 있는 것을 추가한다 (아이템, 일시정지, 생명 등)
- **다음 주 최종 점검에 그대로 쓴다**

### Step 5. 리팩터링 (8분)

**딱 하나만** 한다. 욕심내지 않는다. 아래 중 하나를 고른다.

**선택지 1 — 그리기 분리 (가장 안전하다)**
```
script.js를 정리해 줘. 동작은 절대 바꾸지 마.
게임 루프 안의 그리기 부분을 draw() 함수로 분리해 줘.
다른 것은 건드리지 마.
```

**선택지 2 — 숫자 모으기**
```
script.js를 정리해 줘. 동작은 절대 바꾸지 마.
흩어져 있는 조정용 숫자(속도, 크기, 개수, 간격, 점수)를
코드 맨 위에 모아서 주석을 달아 줘.
값은 바꾸지 말고 위치만 옮겨 줘.
```

**선택지 3 — 중복 제거**
```
script.js를 정리해 줘. 동작은 절대 바꾸지 마.
같은 코드가 두 번 이상 반복되는 곳이 있으면 함수로 묶어 줘.
그 외에는 건드리지 마.
```

**정리한 뒤 Step 4의 체크리스트로 전부 확인한다.** 하나라도 깨졌으면 **되돌린다** (2장 되돌리기). 리팩터링은 하지 않는 것이 깨뜨리는 것보다 낫다.

> **"클래스로 바꿔 줘", "모듈로 분리해 줘" 같은 요청은 하지 않는다.** 코드가 깔끔해 보이지만, **내가 설명할 수 없는 코드가 되면 10장 평가에서 손해다.**

통과하면 커밋한다 (`코드 정리 — 동작 변경 없음`).

### Step 6. 모바일 대응 (10분)

**1단계는 모두 한다.**

```
휴대폰에서도 화면이 제대로 보이게 해 줘.

- index.html에 viewport meta 태그를 추가해 줘
- canvas가 화면 폭을 넘지 않게 CSS로 max-width: 100%를 적용해 줘
- 단, canvas의 width/height 속성 값은 바꾸지 말아 줘 (좌표 계산이 깨지니까)
- 마우스/터치 좌표를 쓰는 부분이 있으면,
  canvas의 실제 크기와 화면에 보이는 크기의 비율로 보정해 줘
- 세로 화면에서도 게임 화면이 잘리지 않게 해 줘
```

**2단계는 내 조작 방식이 쉬운 경우에만 한다.**

```
터치 조작을 추가해 줘.

- (마우스 따라가기라면) touchmove로 같은 동작을 하게 해 줘
- (클릭/점프라면) 화면을 탭하면 (클릭/점프)와 같게 해 줘
- (좌우 이동이라면) 화면 왼쪽 절반을 누르면 왼쪽, 오른쪽 절반을 누르면 오른쪽으로
- 터치할 때 화면이 스크롤되거나 확대되지 않게 preventDefault를 넣어 줘
- 키보드 조작은 그대로 유지해 줘
```

**어려운 조작이라면 솔직하게 적는다.**

```
시작 화면에 "PC에서 방향키로 플레이해 주세요" 한 줄을 추가해 줘.
작은 글씨로, 화면 아래쪽에.
```

**커밋 → Sync → 휴대폰으로 배포 주소를 직접 열어 본다.** 이것이 이번 주의 마지막 확인이다.

## 4. 내 게임에 적용하기 (과제)

### 과제 1. 플레이테스트 기록 (필수)

`my-game` 폴더에 **`플레이테스트.md`** 파일을 만든다.

- [ ] **2명 이상**의 기록이 Step 1의 양식으로 들어 있다
- [ ] 그중 **1명 이상은 내 게임을 처음 보는 사람**이다
- [ ] 테스터가 한 말이 **그대로** 적혀 있다 (요약하지 않는다)
- [ ] 끝난 뒤 세 질문의 답이 적혀 있다
- [ ] **각 테스터의 점수와 내 기록**이 비교되어 있다

### 과제 2. 피드백 반영 내역 (필수)

같은 파일 아래에 Step 2의 표를 넣는다.

- [ ] 들은 말(처방)과 **실제 증상**이 구분되어 있다
- [ ] 의심 원인이 적혀 있다
- [ ] 우선순위가 매겨져 있다
- [ ] **반영한 것 2개 이상**, 각각 무엇을 어떻게 바꿨는지
- [ ] **미반영 항목에 이유**가 적혀 있다 ⭐

> 마지막 항목이 중요하다. **"반영하지 않기로 한 판단"도 설계다.** "보스를 넣자는 의견을 받았지만 남은 1주로는 불가능하고, 지금 게임의 핵심 재미와도 거리가 있어 반영하지 않았다" — 이런 기록이 높은 점수를 받는다.

### 과제 3. 개선 버전 배포 (필수)

- [ ] 1순위 피드백 **2개 이상**이 반영되어 있다
- [ ] 개선 후 **체크리스트 전 항목**이 통과한다
- [ ] `테스트목록.md`가 저장소에 있다
- [ ] 배포 주소에 반영되어 있다

### 과제 4. 모바일 대응 (필수)

- [ ] `viewport` meta 태그가 있다
- [ ] 휴대폰에서 **화면이 잘리지 않고** 보인다
- [ ] 터치 조작을 넣었거나, **못 한다고 명시**했다 (시작 화면 + README)
- [ ] 휴대폰에서 직접 확인했다

### 과제 5. 선택 과제

- 세 번째 테스터에게 받는다 (가족, 다른 과 친구 등)
- 개선 **전/후를 비교**한다 — 같은 사람에게 다시 플레이시켜 본다
- 2순위 항목까지 반영한다
- 터치 조작을 **화면에 버튼으로** 그린다
- 다른 사람의 게임에 **좋은 피드백을 남겨 준다** (상대의 `플레이테스트.md`에 인용되면 가점)

### 과제 6. 회고 파일 (필수)

양식은 **부록 E**와 같다. 9주차는 아래를 포함한다.

- **1번:** 리팩터링 요청을 그대로 복사한다. **"동작은 바꾸지 마"를 넣었는지** 확인한다
- **2번:** 막힌 점. **이번 주는 "남이 플레이하는 것을 보며 알게 된 것"을 써도 된다.** 가장 충격적이었던 관찰 하나를 쓰면 좋다
- **3번:** 코드 설명. **이번 주는 "내가 숫자를 바꿔서 해결한 문제"를 설명한다.** 어느 변수를 왜 그 값으로 바꿨는지

## 다음 주 예고

10장은 **완성과 발표**다. 새 기능은 넣지 않는다. 최종 점검을 하고, `README.md`를 제대로 쓰고, **3분 발표**를 준비한다.

발표에서 말할 것은 세 가지다. **내 게임을 보여 주고, 가장 어려웠던 문제를 어떻게 뚫었는지 말하고, 코드 한 부분을 설명한다.** 10주 동안 매주 회고에 써 온 것이 발표 자료가 된다.

**다음 주 전에 할 일:**
1. 회고 파일을 1주차부터 **다시 읽어 본다.** 가장 기억에 남는 막힘이 무엇이었는지 고른다
2. 발표에서 설명할 **코드 한 부분**을 미리 정해 둔다 (7장의 설명문을 써도 된다)

## 이번 주 자주 막히는 지점

| 증상 | 원인과 해결 |
|---|---|
| 테스터가 "재미있었어"만 말한다 | 2.2의 세 질문으로 바꿔 묻는다. "재미있었어?"는 묻지 않는다 |
| 테스터가 금방 포기한다 | **그게 결과다.** 시작 난이도와 조작법 표시를 의심한다 |
| 피드백이 서로 반대다 | 빈도로 판단한다. 1명 대 1명이면 **내 기획 의도**를 기준으로 결정하고 이유를 적는다 |
| 고칠 게 너무 많다 | 1순위 2~3개만. 나머지는 기록만 해도 과제는 충족된다 |
| 리팩터링 후 게임이 깨졌다 | **되돌린다.** 하나씩 다시 하거나, 하지 않는다 |
| AI가 클래스·모듈 구조로 바꿔 버렸다 | 되돌린다. "내가 이해할 수 있는 수준으로 유지해 줘"를 붙여 다시 요청 |
| 휴대폰에서 canvas가 잘린다 | `viewport` meta 태그 / `max-width: 100%` 확인 |
| 휴대폰에서 글씨가 너무 작다 | `viewport` 태그가 없어서 축소된 것이다 |
| 휴대폰에서 터치 위치가 어긋난다 | canvas 실제 크기와 보이는 크기의 **비율 보정**이 빠졌다 |
| 터치하면 화면이 스크롤된다 | 터치 이벤트에 `preventDefault`가 없다 |
| 휴대폰에서 소리가 안 난다 | 기기 음소거 / 첫 탭 이후에 재생되는지 확인 (8장의 자동 재생 제한) |
| 고친 게 배포에 반영되지 않았다 | 커밋+Sync 확인 → `Ctrl+F5` 강력 새로고침 |

모르는 용어는 **부록 C**, 에러는 **부록 D**, 프롬프트는 **부록 B**, 양식은 **부록 E**를 본다.
