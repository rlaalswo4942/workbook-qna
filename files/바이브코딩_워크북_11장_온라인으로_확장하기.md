## 2. 개념 설명

### 2.1 지금까지 못 했던 것

8장에서 `localStorage`로 최고 점수를 저장했다. 그런데 그건 **내 브라우저에만** 남는다.

```
내 컴퓨터의 최고 점수: 120점   ← localStorage
친구 컴퓨터의 최고 점수: 80점   ← 친구의 localStorage

둘은 서로를 모른다.
```

전체 랭킹을 만들려면 **모두가 같은 곳에 점수를 적어야 한다.** 그 "같은 곳"이 내 컴퓨터에도, 친구 컴퓨터에도 있을 수 없으니, **어딘가 바깥에** 있어야 한다.

| | 어디에 저장되나 | 누가 볼 수 있나 |
|---|---|---|
| `localStorage` | 그 사람의 브라우저 | 그 사람만 |
| **서버/데이터베이스** | 인터넷상의 한 곳 | 모두 |

지금까지 우리가 만든 것은 **정적(static) 웹페이지**다 — HTML/CSS/JS 파일만 있고, GitHub Pages가 그 파일을 그대로 내려 줄 뿐이다. 파일을 내려 주는 곳에는 "점수를 기록해 둘 공간"이 없다.

그래서 이번 주에 하나를 추가한다. **데이터를 보관해 주는 서비스**다.

### 2.2 API — 서비스에 말을 거는 창구

**API(Application Programming Interface)는 "프로그램이 다른 프로그램에 요청을 보내는 창구"** 다.

식당으로 비유하면 이렇다.

```
손님(내 게임)  →  주문서(요청)  →  주방 창구(API)  →  주방(서버)
                                                      ↓
손님(내 게임)  ←  음식(응답)    ←  주방 창구(API)  ←
```

손님은 주방에 들어가지 않는다. **정해진 창구로, 정해진 양식의 주문서만** 보낸다. 주방이 어떻게 생겼는지 알 필요도 없다. API가 그 창구다.

**요청에는 네 가지가 들어간다.**

| 항목 | 뜻 | 예 |
|---|---|---|
| **주소(URL)** | 어느 창구인가 | `https://....../scores` |
| **방식(method)** | 무엇을 하려는가 | `GET`(읽기) / `POST`(쓰기) |
| **헤더(header)** | 신분증과 양식 | 키, `Content-Type` |
| **본문(body)** | 보낼 내용 | `{"name":"지민","score":120}` |

**방식은 네 개만 알면 된다.**

| 방식 | 하는 일 |
|---|---|
| `GET` | 가져온다 (랭킹 읽기) |
| `POST` | 새로 만든다 (점수 등록) |
| `PATCH` / `PUT` | 고친다 |
| `DELETE` | 지운다 |

### 2.3 `fetch` — 요청을 보내는 명령

JavaScript에서 API를 부르는 명령은 `fetch`다. 먼저 **키가 필요 없는 공개 API**로 연습한다.

```javascript
async function getData() {
  const res = await fetch("https://api.example.com/something");  // 요청을 보낸다
  const data = await res.json();                                 // 받은 걸 해석한다
  console.log(data);
}
```

처음 보는 단어가 두 개 있다.

**`async` / `await` — "기다린다"**

인터넷 요청은 **시간이 걸린다.** 0.1초일 수도, 3초일 수도 있다. 그래서 "답이 올 때까지 기다려라"라고 표시해야 한다. 그게 `await`이고, `await`을 쓰는 함수 앞에는 `async`를 붙인다.

```
await 없이 쓰면  →  "아직 안 온 답"을 가지고 계산해서, undefined가 나온다
```

3장에서 이미지를 `img.onload` 안에서 그려야 했던 것과 같은 문제다. **"준비되기 전에 쓰면 안 된다."**

**`.json()` — 받은 글자를 쓸 수 있는 형태로**

서버가 보내 주는 데이터는 **JSON**이라는 글자 형식이다. 객체·배열과 거의 똑같이 생겼다.

```json
[
  { "name": "지민", "score": 120 },
  { "name": "서연", "score": 95 }
]
```

`res.json()`을 거치면 이게 6장에서 쓴 **객체 배열**이 된다. 그러면 `for` 반복문으로 그려 낼 수 있다. **랭킹 표시는 결국 6장에서 배운 것과 같은 작업이다.**

**중요: 인터넷 요청은 실패한다**

와이파이가 끊기고, 서버가 느리고, 오타가 있다. 그래서 실패를 대비해야 한다.

```javascript
try {
  const res = await fetch(url);
  const data = await res.json();
  // 성공했을 때
} catch (e) {
  console.log("랭킹을 불러오지 못했습니다", e);
  // 실패해도 게임은 계속되어야 한다
}
```

`try ... catch`는 **"해 보고, 실패하면 이렇게 해라"** 다. 이 장의 모든 요청에 붙인다.

> **원칙: 랭킹이 안 되더라도 게임은 플레이할 수 있어야 한다.** 서버가 죽었을 때 게임까지 멈추면 안 된다. 발표 당일에 이게 생명을 구한다.

### 2.4 API 키 — 이 장에서 가장 중요한 부분

대부분의 서비스는 **"누가 보낸 요청인가"** 를 확인한다. 그 신분증이 **API 키**다.

그런데 여기에 2장부터 이어진 문제가 걸린다.

> **내 저장소는 Public이다. 내 JavaScript 파일은 누구나 볼 수 있다.**

브라우저에서 `F12` → Sources, 또는 그냥 GitHub 저장소를 열면 **내 코드가 그대로 보인다.** 그 안에 키가 적혀 있으면 키도 보인다.

```
내 script.js 안에 키를 적는다
  → GitHub Pages로 배포된다
  → 누구나 F12로 열어 볼 수 있다
  → 키가 노출된다
```

**숨길 방법은 없다.** 난독화도, 변수 이름 바꾸기도, 다른 파일로 분리하기도 소용없다. 브라우저가 실행하려면 브라우저가 읽을 수 있어야 하고, 브라우저가 읽을 수 있으면 사람도 읽을 수 있다.

그래서 **키를 두 종류로 나눠서 생각해야 한다.**

| | 공개용 키 | 비밀 키 |
|---|---|---|
| 부르는 이름 | publishable / public / anon | secret / service_role / private |
| 공개 | **공개되도록 설계된 것** | **절대 공개 금지** |
| 할 수 있는 일 | 서버가 허락한 것만 | **전부** (모든 데이터 읽기·삭제) |
| 브라우저 코드에 | 넣어도 된다 | 넣으면 안 된다 |
| 보호 수단 | **서버 쪽 접근 규칙** | 비밀 유지 그 자체 |

**핵심은 이것이다.**

> **공개용 키는 "비밀"로 지키는 게 아니라, 그 키로 할 수 있는 일을 서버에서 제한해서 지킨다.**

그래서 이번 주 작업의 절반은 코드가 아니라 **"이 키로 무엇까지 할 수 있는가"를 서버에서 설정하는 일**이다.

> **참고: 키 이름이 바뀌는 중이다.** Supabase는 기존 `anon` / `service_role` 키를 **`sb_publishable_...` / `sb_secret_...`** 형태의 새 키로 옮기고 있다. 화면에 어느 이름이 보이든 판단 기준은 같다 — **"publishable/public/anon"이면 공개용, "secret/service"가 붙으면 절대 공개 금지.** 헷갈리면 서비스 문서에서 그 키가 공개용인지 확인한다.

**비밀 키를 실수로 올렸다면**

```
1. 즉시 서비스 대시보드에서 그 키를 폐기(revoke)하거나 새로 발급한다
2. 코드에서 지운다
```

**2번만 하면 안 된다.** Git은 모든 이력을 보관하므로, **커밋 이력에 남아 있는 키는 지워도 조회할 수 있다.** 그래서 1번이 먼저다. 이건 실제 업무에서도 똑같이 적용되는 절차다.

**키를 아예 코드에 안 넣는 방법도 있다**

진짜 비밀 키가 필요한 작업(결제, 관리자 기능, 유료 AI API 호출 등)은 **중간에 서버를 하나 두고** 그 서버만 비밀 키를 갖게 한다.

```
브라우저  →  내 서버(키 보관)  →  유료 API
```

이걸 **서버리스 함수**(Netlify Functions, Vercel Functions, Supabase Edge Functions 등)로 만들 수 있는데, **이 수업의 범위를 넘는다.** 다만 **"브라우저에 비밀 키를 둘 수 없을 때는 중간에 서버를 둔다"** 는 해결 방향은 기억해 둔다. 12장에서 게임에 AI 기능을 넣고 싶을 때 바로 이 문제가 나온다.

### 2.5 어디에 저장할까

점수를 보관해 줄 서비스가 필요하다. 조건은 셋이다 — **무료 범위가 있고, 브라우저에서 바로 호출할 수 있고, 접근 규칙을 설정할 수 있어야 한다.**

| 선택지 | 특징 |
|---|---|
| **Supabase** | 표 형태 데이터베이스. REST로 바로 호출 가능. 접근 규칙(RLS)이 명확하다 |
| **Firebase** | 구글 서비스. 문서형 데이터베이스. 규칙 문법을 따로 배워야 한다 |
| 그 밖의 백엔드 서비스 | 비슷한 구조. 무료 범위와 규칙 설정 방식만 확인한다 |

**이 장의 실습은 Supabase를 예로 쓴다.** 라이브러리를 설치하지 않고 `fetch`만으로 쓸 수 있어서, 이 수업의 "순수 HTML/CSS/JS" 원칙을 유지할 수 있기 때문이다.

> ⚠️ **화면과 메뉴 이름은 자주 바뀐다.** 아래 단계가 실제와 다르면, **메뉴 이름보다 목적**을 기준으로 찾는다. 목적은 네 가지다 — ① 프로젝트 만들기 ② 표 만들기 ③ **공개용 키와 접근 규칙 확인** ④ 주소 확인. 막히면 공식 문서를 본다.

### 2.6 접근 규칙 — 랭킹에 필요한 권한은 둘뿐이다

랭킹 기능에 필요한 권한을 적어 보면 생각보다 적다.

| 동작 | 필요한가 | 누구에게 |
|---|---|---|
| 점수 목록 읽기 | **필요** | 누구나 |
| 내 점수 추가 | **필요** | 누구나 |
| 남의 점수 수정 | 필요 없다 | 아무도 |
| 점수 삭제 | 필요 없다 | 아무도 (관리자만, 대시보드에서 직접) |

그래서 **읽기(select)와 추가(insert)만 허용하고, 수정과 삭제는 막는다.** 이렇게 하면 공개용 키가 노출되어도 남이 할 수 있는 최악은 "장난 점수를 추가하는 것"까지다. 데이터가 통째로 지워지는 일은 없다.

Supabase에서는 이것을 **RLS(Row Level Security, 행 수준 보안)** 로 설정한다. 이름은 어려워 보이지만 하는 일은 단순하다.

> **"이 표에 대해, 누가, 어떤 동작을 할 수 있는가"를 정하는 것.**

**RLS를 켜지 않으면 어떻게 되는가** — 표가 사실상 전부 열린 상태가 된다. 공개용 키만 있으면 누구나 전체 삭제도 가능하다. **그래서 RLS는 선택이 아니다.** 이 장에서 가장 많이 나는 사고가 "RLS를 켜지 않고 배포하는 것"이다.

**꼭 알아야 할 성질: RLS 차단은 "에러"가 아니다**

차단될 때 무엇이 오는지가 동작마다 다르다. 이걸 모르면 "막혔는지 안 막혔는지"를 거꾸로 판단한다.

| 동작 | 정책이 없을 때 오는 것 |
|---|---|
| 읽기(SELECT) | **에러가 아니라 빈 목록** `200` + `[]` — "랭킹이 비어 보인다" |
| 등록(INSERT) | `403` 에러 |
| 수정·삭제(UPDATE/DELETE) | **에러가 아니라 "0개 처리"** `204` — 요청은 성공처럼 보이고 아무것도 안 바뀐다 |

> **그래서 삭제가 막혔는지는 응답 코드로 확인할 수 없다.** "요청이 성공했다"고 나와도 실제로는 아무 행도 지워지지 않은 것이다. **확인 방법은 표의 행 수가 그대로인지 직접 보는 것**이다 (Step 6에서 그렇게 한다).

### 2.7 보낸 점수를 믿을 수 없다

마지막으로, 알고 있어야 할 한계가 있다.

브라우저에서 점수를 보낸다는 것은, **브라우저를 쓰는 사람이 아무 숫자나 보낼 수 있다**는 뜻이다. `F12` 콘솔에서 직접 요청을 보내면 플레이하지 않고도 999999점을 올릴 수 있다.

**이건 내 코드가 허술해서가 아니다.** 브라우저에서 오는 모든 데이터가 원래 그렇다. 상용 게임들이 점수 계산을 서버에서 하는 이유가 이것이다.

> **보안의 기본 원칙: 클라이언트(브라우저)가 보낸 것은 믿지 않는다.**

이 수업 범위에서 할 수 있는 **완화책**은 이 정도다.

| 방법 | 어디에서 | 실제 효과 |
|---|---|---|
| 상한을 둔다 (예: 100만 점 초과 거절) | 브라우저 코드 | **정상 사용자의 실수만 막는다.** 조작하려는 사람에게는 효과 0 |
| 플레이 시간도 함께 보낸다 | 브라우저 코드 | 같다. 시간도 조작할 수 있다 |
| **같은 제한을 표에도 걸어 둔다** | **서버(DB)** | **실제로 막힌다** ⭐ |
| 이름 길이·글자를 제한한다 | 둘 다 | 표시 깨짐과 욕설을 줄인다 |
| 부정 기록을 지울 수 있게 대시보드를 열어 둔다 | — | 사후 대응 |

**세 번째 줄이 핵심이다.** 브라우저에 적은 제한은 브라우저를 쓰는 사람이 지나갈 수 있지만, **표(데이터베이스)에 걸어 둔 제한은 지나갈 수 없다.** 점수 범위와 이름 길이는 서버 쪽에 함께 걸어 둔다.

```sql
-- 등록 정책에 조건을 함께 걸면, 조건을 벗어난 요청은 거부된다
create policy "점수 등록 허용" on scores for insert to anon
  with check (score >= 0 and score <= 1000000 and char_length(name) between 1 and 8);
```

**등록 시각도 서버가 정하게 한다.** `created_at`을 브라우저가 보내면 날짜도 조작할 수 있어서, 주간 랭킹 같은 것이 무의미해진다. 열의 기본값을 `now()`로 두고 **브라우저는 그 열을 아예 보내지 않는다.**

**완전한 해결은 서버에서 게임을 검증하는 것**이고, 그건 이 수업 범위를 넘는다. 다만 **한계를 알고 쓰는 것과 모르고 쓰는 것은 다르다.** 과제 회고에 이 한계를 쓰는 것이 이번 주 평가 항목이다.

### 공개 랭킹에 적을 것과 적지 않을 것

이 표는 **누구나 읽을 수 있다.** 그래서 두 가지를 지킨다.

**① 개인정보를 받지 않는다.** 닉네임만 받는다. 실명, 학번, 학과, 연락처는 입력받지도 저장하지도 않는다. 시작 화면이나 입력 안내에 "닉네임을 입력하세요"라고 쓴다.

**② 이름은 반드시 "글자"로만 그린다.** 우리 실습은 `ctx.fillText`로 Canvas에 그리므로 안전하다. 그런데 랭킹을 HTML로 표시하고 싶어서 `innerHTML`에 넣으면, **누구나 등록할 수 있는 칸에 남이 코드를 적어 넣을 수 있다.** 그러면 내 페이지를 여는 모든 사람의 브라우저에서 그 코드가 실행된다.

```javascript
el.innerHTML = name;     // ❌ 남이 적은 것이 코드로 실행될 수 있다
el.textContent = name;   // ⭕ 무엇이 적혀 있어도 글자로만 표시된다
ctx.fillText(name, x, y) // ⭕ Canvas는 글자로만 그린다
```

**규칙 하나로 정리하면 — 남이 적은 것을 화면에 보여 줄 때는 `textContent`나 `fillText`를 쓴다.**

## 3. 따라 하기 실습

작업 폴더는 **`my-game`** 이다.

> **시작 전에 커밋한다.** 소스 제어 → `11장 시작 전 상태` → Commit.
>
> 이번 주는 **외부 서비스**를 붙인다. 잘못되면 게임이 아예 안 뜨는 상황도 생기므로, 돌아올 지점이 특히 중요하다.

### Step 1. 키 없는 API로 `fetch` 연습 (10분)

서비스 가입 전에, **`fetch`가 어떻게 동작하는지만** 먼저 본다.

```
script.js에 fetch 연습용 코드를 추가해 줘.

- 키가 필요 없는 공개 API 하나를 호출해서 결과를 콘솔에 출력해 줘
  (예: 무료 랜덤 명언 API, 공개 시간 API 등 가입 없이 쓸 수 있는 것)
- async/await를 쓰고, try/catch로 실패를 처리해 줘
- 각 줄에 한국어 주석을 달아 줘
- 게임 코드는 건드리지 마. 연습용으로 따로 함수 하나만 추가해 줘
```

`F12` 콘솔을 열고 확인한다.

- [ ] 데이터가 콘솔에 출력된다
- [ ] 객체나 배열 형태로 보인다 (6장에서 본 모양)
- [ ] **네트워크를 끊고 새로고침해 본다** → `catch`로 넘어가고, **게임은 계속 돈다**

마지막 항목이 이 단계의 핵심이다. **실패해도 게임이 멈추지 않는 구조**를 먼저 확인한다.

> 공개 API가 응답하지 않으면 다른 것을 쓴다. 중요한 건 특정 API가 아니라 `fetch`의 흐름이다.

확인 후 이 연습 코드는 주석 처리하거나 지운다.

### Step 2. 서비스 가입과 표 만들기 (12분)

**Supabase 기준**이다. 화면이 다르면 목적을 기준으로 찾는다.

1. [supabase.com](https://supabase.com) → 가입 (GitHub 계정으로 가능)
2. **New project** → 이름은 `my-game-rank` 같은 영어로. 비밀번호는 적어 둔다
3. 프로젝트가 준비되면 **Table Editor** → **New table**
4. 표를 만든다

| 설정 | 값 |
|---|---|
| 표 이름 | `scores` |
| **RLS 활성화** | **반드시 켠다** ⭐ (기본으로 켜져 있으면 그대로) |

5. 열(column)을 추가한다

| 열 이름 | 형식 | 설명 |
|---|---|---|
| `id` | 자동 생성 | 건드리지 않는다 |
| `created_at` | 자동 생성 (시각) | 건드리지 않는다 |
| `name` | text | 플레이어 이름 |
| `score` | int (정수) | 점수 |

> **RLS 켜는 것을 확인한다.** 이걸 빠뜨리면 공개용 키로 누구나 전체 삭제가 가능해진다. 표 목록에서 `scores` 옆에 RLS 상태가 표시되니 확인한다.

### Step 3. 접근 규칙(RLS) 설정 (10분) — 이번 주 핵심

표를 만들어도 RLS가 켜져 있으면 **아직 아무것도 할 수 없다.** 허용 규칙을 두 개 추가한다.

1. 표 화면에서 **RLS 정책(Policies)** 으로 들어간다
2. 규칙 두 개를 만든다

| 규칙 | 동작 | 대상 |
|---|---|---|
| 랭킹 읽기 허용 | `SELECT` | 모두 (anon/public) |
| 점수 등록 허용 | `INSERT` | 모두 (anon/public) |

3. **`UPDATE`와 `DELETE` 규칙은 만들지 않는다.** 규칙이 없으면 차단이다 — 그게 우리가 원하는 상태다.

SQL로 직접 넣는 방식이 더 확실하면, AI에게 이렇게 요청한다.

```
Supabase의 scores 표에 RLS 정책을 만드는 SQL을 알려 줘.

- 누구나(anon) SELECT 할 수 있게
- 누구나(anon) INSERT 할 수 있게. 단 with check로 아래 조건을 함께 걸어 줘
  · score는 0 이상 100만 이하
  · name은 1~8글자
- UPDATE와 DELETE는 아무도 할 수 없게 (정책을 만들지 않는 방식으로)
- created_at은 기본값 now()를 쓰게 하고, 브라우저는 그 열을 보내지 않을 거야

SQL Editor에 붙여넣을 수 있는 형태로 주고, 각 줄이 무슨 뜻인지 설명해 줘.
```

**왜 `with check`까지 넣는가** — 2.7에서 다룬다. 브라우저 코드에 적은 제한은 조작하는 사람이 지나갈 수 있지만, **정책에 걸어 둔 조건은 지나갈 수 없다.**

**확인 방법** — 규칙을 넣은 뒤 다음 단계에서 읽기와 쓰기가 되는지 직접 테스트한다. 안 되면 거의 항상 RLS 규칙 문제다. 단, **차단이 에러로 오지 않는 경우가 있다**는 것을 기억한다 (2.6의 표).

### Step 4. 키와 주소 확인 (5분)

1. 프로젝트 설정에서 **API 키** 화면으로 간다
2. 두 가지를 찾는다

| 찾을 것 | 어디에 쓰나 |
|---|---|
| **프로젝트 URL** | 요청 주소 |
| **공개용 키** (`sb_publishable_...` 또는 `anon`) | 코드에 넣는다 |

3. **비밀 키(`sb_secret_...` / `service_role`)는 복사하지도 않는다.** 실수로 붙여넣을 가능성을 없애는 게 가장 안전하다.

> **지금 확인하는 습관** — 코드에 키를 넣은 뒤, 그 키가 **공개용인지** 다시 한 번 본다. `secret`이나 `service`라는 글자가 보이면 멈추고 지운다.

### Step 5. 점수 등록과 랭킹 읽기 (15분)

AI에게 요청한다. **한 번에 다 하지 않고 등록 → 읽기 순서로** 한다.

**(1) 점수 등록**

```
게임 오버 시 점수를 Supabase에 등록하는 기능을 추가해 줘.

- Supabase REST API를 fetch로 직접 호출해 줘 (라이브러리는 쓰지 말고)
- 표 이름은 scores, 열은 name(text)과 score(int)
- 프로젝트 URL과 공개용 키는 코드 위쪽에 변수로 모아 주고,
  "공개용 키 — 비밀 키를 넣지 말 것"이라는 주석을 달아 줘
- 게임 오버가 되면 이름을 입력받고(prompt 또는 화면 입력), 점수와 함께 등록해 줘
- 이름은 공백 제거 후 1~8글자로 제한하고, 비어 있으면 "익명"으로 해 줘
- 점수가 비정상적으로 크면(예: 100만 초과) 보내지 말아 줘
- try/catch로 감싸서, 등록이 실패해도 게임은 계속되게 해 줘
- 등록 중에는 "등록 중...", 성공하면 "등록 완료", 실패하면
  "등록 실패 — 오프라인일 수 있어요"를 화면에 표시해 줘
- 한국어 주석을 달아 줘
```

Supabase 대시보드의 Table Editor를 열어 **행이 실제로 추가되는지** 눈으로 확인한다. 이게 가장 확실한 테스트다.

**(2) 랭킹 읽기**

```
상위 랭킹을 불러와 화면에 표시해 줘.

- scores 표에서 score 기준 내림차순 상위 10개를 가져와 줘
- 게임 오버 화면(또는 시작 화면)에 "1. 지민 — 120" 형태로 목록을 그려 줘
- Canvas에 ctx.fillText로 그려 줘 (HTML 요소를 새로 만들지 말고)
- 불러오는 동안에는 "랭킹 불러오는 중..."을 표시해 줘
- 실패하면 "랭킹을 불러올 수 없습니다"만 표시하고 게임은 정상 작동하게 해 줘
- 랭킹은 게임 오버될 때마다 다시 불러오게 해 줘
```

확인한다.

- [ ] 랭킹이 화면에 보인다
- [ ] 점수 순으로 정렬되어 있다
- [ ] 한 판 더 하면 내 기록이 목록에 들어간다
- [ ] **콘솔에 에러가 없다**

> **403 / 401 에러가 나면 RLS 규칙 문제다.** 읽기가 안 되면 SELECT 규칙, 등록이 안 되면 INSERT 규칙을 확인한다. 부록 D.8을 본다.

### Step 6. 보안 점검 (8분) — 건너뛰지 않는다

**이번 주에서 가장 중요한 단계다.** 배포 전에 반드시 한다.

**(1) 코드 안의 키 확인**

`script.js`에서 키를 찾아 확인한다.

- [ ] 키 이름에 `publishable`, `public`, `anon` 중 하나가 들어 있다
- [ ] `secret`, `service`, `service_role` 이라는 글자가 **어디에도 없다**
- [ ] 키 옆에 "공개용 키" 주석이 있다

**(2) 커밋 이력 확인**

```
git log -p 에서 secret이나 service_role 키가 들어간 적이 있는지 확인하고 싶어.
VS Code에서 확인하는 방법을 알려 주고, 터미널 명령어도 함께 알려 줘.
```

실수로 올린 적이 있으면 **즉시 서비스 대시보드에서 그 키를 재발급**한다. 코드에서 지우는 것만으로는 부족하다.

**(3) 권한 확인 — 직접 테스트한다**

2.6에서 본 것을 기억한다. **삭제 차단은 에러로 오지 않는다.** 응답 코드로 판단하면 "삭제가 성공했다"고 잘못 읽는다. 그래서 **표의 행 수로 확인한다.**

1. Supabase **Table Editor**를 열어 두고, 지워도 되는 테스트 행 하나의 `id`를 확인한다 (예: 3)
2. **현재 행 수를 적어 둔다**
3. 배포된 페이지에서 `F12` 콘솔을 열고, 그 행을 지우는 요청을 보낸다

```
내 Supabase scores 표에서 id가 3인 행 하나를 지우는 DELETE 요청을
브라우저 콘솔에서 보내 보는 fetch 코드를 알려 줘.
응답 코드와 응답 본문을 둘 다 출력하게 해 줘.
```

4. **Table Editor를 새로고침한다**

| 결과 | 뜻 |
|---|---|
| **행 수가 그대로다** | ⭕ 정상. 차단되고 있다 (응답이 `204`로 성공처럼 보여도 괜찮다) |
| 행이 사라졌다 | ⚠️ DELETE 정책이 있다. Step 3으로 돌아가 **삭제 정책을 지운다** |

> **응답 코드만 보고 Step 3을 다시 손대지 않는다.** `204`가 왔다고 정책을 추가하면 오히려 구멍이 생긴다. 판단 기준은 **행 수**다.
>
> 이 테스트는 **내 표에 대해서만** 한다. 남의 서비스에 같은 시도를 하는 것은 공격이고, 불법이 될 수 있다.

### Step 7. 커밋과 배포 (5분)

1. `README.md`에 아래를 추가한다

```markdown
## 온라인 랭킹
- 백엔드: Supabase (무료 범위)
- 저장하는 것: 플레이어 이름(최대 8자), 점수, 등록 시각
- 접근 규칙: 읽기와 등록만 허용, 수정·삭제 차단 (RLS)
- 서버 쪽 제한: 점수 0~100만, 닉네임 1~8자, 등록 시각은 서버가 기록
- 저장하지 않는 것: 실명, 학번, 연락처 (닉네임만 받는다)
- 코드에 포함된 키는 **공개용 키**이며, 접근 규칙으로 보호된다
- 한계: 브라우저에서 보낸 점수는 검증할 수 없다 (2.7 참고)
```

2. 커밋 → Sync → **시크릿 모드로 배포 주소를 열어** 확인한다

> **발표 전날 확인할 것** — 무료 플랜 프로젝트는 **한동안 쓰지 않으면 일시정지**될 수 있다. 그러면 랭킹이 죽는다. 발표 전에 한 번 플레이해서 깨어 있는지 확인하고, 랭킹이 실패해도 게임은 돌아가는지(과제 1의 ⭐ 항목) 다시 본다.

- [ ] 랭킹이 보인다
- [ ] 점수가 등록된다
- [ ] 휴대폰에서도 된다

## 이번 주 자주 막히는 지점

| 증상 | 원인과 해결 |
|---|---|
| `undefined`가 출력된다 | `await`을 빠뜨렸다. 요청이 끝나기 전에 값을 썼다 |
| `401` 에러 | 키나 `apikey` 헤더 문제다. RLS와 무관 — 키가 잘렸거나 헤더가 빠졌다 |
| `403` 에러 | INSERT가 RLS나 `with check` 조건에 걸렸다 |
| 랭킹이 **빈 목록**으로 온다 (에러 없음) | SELECT 정책이 없다. **차단이 에러로 오지 않는다** |
| RLS를 켰는데 아무것도 안 된다 | **정상이다.** 규칙을 만들어야 허용된다 (Step 3) |
| CORS 에러가 난다 | 그 서버가 브라우저 호출을 허용하지 않는 것이다. **내 코드로는 고칠 수 없다** — 허용하는 API로 바꾼다. 부록 D.8 |
| 점수가 글자로 저장된다 | 열 형식이 text다. int로 만들고, 보낼 때 `Number()`로 변환 |
| 정렬이 이상하다 | 같은 원인. 글자로 저장되면 `"9" > "100"`이 된다 (8장과 같은 문제) |
| 랭킹이 안 뜨는데 에러도 없다 | `try/catch`가 에러를 삼키고 있다. `catch` 안에서 `console.log(e)` 확인 |
| 게임이 아예 안 뜬다 | 요청 코드에 문법 오류. 콘솔 첫 에러를 본다 / 시작 전 커밋으로 되돌린다 |
| 등록이 중복으로 여러 번 된다 | 게임 오버 상태에서 매 프레임 호출되고 있다. **한 번만** 보내도록 조건을 둔다 |
| 로컬은 되는데 배포하면 안 된다 | 키·주소 오타 / 파일 커밋 누락 / HTTPS 문제 |
| 키를 실수로 올렸다 | **먼저 재발급**하고, 그다음 코드에서 지운다. 순서가 중요하다 |

모르는 용어는 **부록 C**, 오류는 **부록 D.8**, 프롬프트는 **부록 B**를 본다.

## 참고

API 키 정책은 서비스마다 다르고 바뀐다. Supabase의 키 종류와 이관에 대해서는 공식 문서([supabase.com/docs](https://supabase.com/docs/guides/getting-started/migrating-to-new-api-keys))를 확인한다. **키 이름이 무엇이든 판단 기준은 하나다 — 이 키로 무엇을 할 수 있는가.**
