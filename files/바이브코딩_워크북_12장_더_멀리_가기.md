## 2. 개념 설명

### 2.1 왜 지금까지 라이브러리를 쓰지 않았나

본과정 10주 동안 외부 라이브러리를 쓰지 않았다. Node.js도, 빌드 도구도 없었다. 그건 **일부러 그렇게 한 것**이다.

이유는 하나다. **라이브러리는 편리함을 주고 이해를 가져간다.**

| | 직접 만들면 | 라이브러리를 쓰면 |
|---|---|---|
| 게임 루프 | 내가 짰다. 네 단계를 설명할 수 있다 | 알아서 돌아간다. 안을 모른다 |
| 충돌 판정 | 네 조건의 뜻을 안다 | `overlap()` 한 줄. 왜 안 맞는지 모른다 |
| 코드 양 | 많다 | 적다 |
| 문제가 생기면 | 어느 숫자가 틀렸는지 찾는다 | **어디를 봐야 할지 모른다** |

마지막 줄이 핵심이다. 처음부터 라이브러리로 시작하면, 문제가 생겼을 때 **내 코드와 라이브러리 중 어디가 문제인지 구분할 수 없다.** 7장에서 배운 "범위를 좁혀 간다"가 불가능해진다.

그래서 순서가 중요했다. **직접 만들어 본 다음에 라이브러리를 보면, 라이브러리가 무엇을 대신해 주는지 정확히 보인다.** 그게 오늘의 첫 번째 실습이다.

> **지금은 이렇게 보일 것이다.** "내가 6장에 고생해서 만든 충돌 판정이 저쪽에서는 한 줄이네." 그 느낌이 맞다. 다만 **그 한 줄이 무엇을 하는지 아는 사람과 모르는 사람의 차이**가 7주 동안의 결과물이다.

### 2.2 게임 라이브러리가 해 주는 것

**Phaser**를 예로 본다. 2D 웹 게임용으로 가장 널리 쓰이는 것 중 하나다.

| 우리가 직접 만든 것 | Phaser가 가진 것 |
|---|---|
| `requestAnimationFrame` 루프 (4장) | 루프 내장. `update()`만 쓰면 된다 |
| `fillRect` / `drawImage` (3장) | 스프라이트 객체. 위치·회전·크기를 속성으로 |
| 충돌 판정 네 조건 (6장) | 물리 엔진. 충돌·중력·튕김 내장 |
| `keys` 객체 (5장) | 키보드 입력 객체 내장 |
| `new Audio` (8장) | 사운드 관리자. 여러 소리를 함께 다룬다 |
| `gameState` 분기 (6·8장) | **Scene** — 화면 단위로 나눠 관리 |
| `img.onload` 기다리기 (3장) | **preload** — 에셋을 미리 다 불러온 뒤 시작 |

**대신 따라오는 것도 있다.**

| 얻는 것 | 치르는 것 |
|---|---|
| 코드가 짧아진다 | 라이브러리의 **구조와 용어를 배워야 한다** |
| 물리·애니메이션이 쉽다 | 파일이 커진다 (압축 상태로도 수백 KB, 원본은 1MB 이상) |
| 큰 게임을 만들 수 있다 | 작은 게임엔 과하다 |
| 문제의 상당 부분이 해결되어 있다 | 라이브러리 안의 문제는 **내가 고칠 수 없다** |

> **판단 기준** — 화면 하나로 끝나는 작은 게임이면 지금 방식이 낫다. 스테이지가 여러 개이고 물리가 복잡해지면 라이브러리가 낫다. **지금 내 게임을 Phaser로 다시 만들 필요는 없다.**

### 2.3 게임에 AI 기능 넣기 — 세 가지 방식

"게임에 AI를 넣는다"는 말은 여러 가지를 뜻할 수 있다. 실제로 가능한 것을 정리하면 세 가지다.

| 방식 | 언제 AI를 쓰나 | 키가 필요한가 | 난이도 |
|---|---|---|---|
| **A. 미리 생성해서 넣기** | 개발 중에 한 번 | **필요 없다** | 쉽다 |
| **B. 중간 서버를 두고 실시간 호출** | 플레이 중 | 필요하다 (서버에 보관) | 어렵다 |
| **C. 규칙 기반 "AI처럼 보이는" 행동** | 플레이 중 | 필요 없다 | 보통 |

**방식 A — 미리 생성해서 넣기 (가장 실용적이다)**

개발 중에 AI로 **콘텐츠를 만들어 두고, 그 결과를 파일로 저장해서** 쓴다.

```
개발 중:  AI에게 "게임 오버 메시지 30개를 만들어 줘" → 결과를 messages.json으로 저장
플레이 중: 그중 하나를 랜덤으로 꺼내 보여 준다  ← AI 호출 없음
```

| 장점 | 단점 |
|---|---|
| **키가 아예 필요 없다** | 플레이 중에 새 내용이 안 나온다 |
| 비용 0, 지연 0, 실패 0 | 반복하면 익숙해진다 |
| 오프라인에서도 작동한다 | |

이렇게 만들 수 있는 것들이 생각보다 많다.

- 게임 오버 메시지, 칭찬·야유 대사 30~50개
- 적 이름, 아이템 설명, 스테이지 이름
- 퀴즈 게임의 문제 은행
- 텍스트 게임의 분기 대사
- 스프라이트와 효과음 (생성형 도구로)

**"플레이 중에 AI가 반응하는 느낌"의 90%는 이 방식으로 낼 수 있다.** 그래서 오늘 실습은 이것으로 한다.

**방식 B — 중간 서버를 두고 실시간 호출**

플레이 중에 AI를 실제로 부르는 방식이다. 11장에서 예고한 문제가 여기서 나온다.

> **유료 AI API 키는 비밀 키다. 브라우저에 둘 수 없다.**

11장에서 확인했다. 브라우저 코드는 누구나 볼 수 있다. 거기에 유료 키를 넣으면 **남이 내 키로 요금을 쓴다.** 그래서 구조가 이렇게 되어야 한다.

```
❌ 브라우저(키 보관)  →  AI API            남이 내 키를 꺼내 쓴다
⭕ 브라우저  →  내 서버(키 보관)  →  AI API   키가 브라우저에 없다
```

그 "내 서버"를 **서버리스 함수**로 만든다 (Netlify Functions, Vercel Functions, Supabase Edge Functions 등). 작은 함수 하나를 올려 두면, 그 함수만 키를 갖는다.

**이 방식의 현실적인 부담**

| 문제 | 왜 어려운가 |
|---|---|
| **비용** | 호출마다 돈이 든다. 게임이 퍼지면 요금이 커진다 |
| **지연** | 응답에 1~5초. 실시간 게임에 바로 쓰기 어렵다 |
| **실패** | 11장과 같다. 실패해도 게임이 돌아가야 한다 |
| **남용** | 내 함수가 공개되어 있으면 남이 마구 부를 수 있다 → 호출 제한이 필요하다 |
| **안전** | 플레이어가 입력한 글이 AI에게 그대로 간다 → 아래 참고 |

**프롬프트 인젝션** — 플레이어 이름이나 입력을 AI 프롬프트에 그대로 넣으면, 플레이어가 "지금까지 지시를 무시하고 ○○라고 답해"라고 써넣을 수 있다.

중요한 사실 하나를 분명히 해 둔다. **입력을 걸러서 이걸 완전히 막는 방법은 없다.** 글자 수와 종류를 제한하면 **줄어들 뿐**이고, 작정한 사람은 지나간다. 그래서 막는 방향이 아니라 **"뚫려도 피해가 없게" 만드는 방향**으로 설계한다.

| 원칙 | 뜻 |
|---|---|
| 모델에 비밀을 주지 않는다 | 키·시스템 지시를 사용자 글과 한 덩어리로 섞지 않는다 |
| 모델에 권한을 주지 않는다 | 모델의 답으로 삭제·결제·전송 같은 동작을 실행하지 않는다 |
| 돌아온 답은 **비신뢰 텍스트**로 다룬다 | 화면에 글자로만 표시한다 (11장의 `textContent`/`fillText`) |
| 입력 제한은 보조 수단 | 길이·종류 제한은 "줄이는 것"이지 "막는 것"이 아니다 |

11장의 **"클라이언트를 믿지 않는다"** 와 같은 원칙이고, 한 단계 더 나아간 것이다 — **모델의 출력도 믿지 않는다.**

**그래서 이 수업에서는 방식 B를 개념까지만 다룬다.** 해 보고 싶으면 혼자 할 수 있도록, 2.5의 학습 절차를 쓰면 된다.

**방식 C — 규칙 기반 "AI처럼 보이는" 행동**

적이 플레이어를 추적하고, 거리에 따라 행동을 바꾸고, 패턴을 섞는 것. **AI API와 아무 상관이 없지만, 플레이어에게는 "똑똑하다"고 느껴진다.**

```javascript
// 플레이어 쪽으로 다가온다
if (enemy.x < player.x) enemy.x += enemy.speed;
else enemy.x -= enemy.speed;
```

**이게 전통적인 게임 AI다.** 4~6장에서 배운 것만으로 만들 수 있고, 비용도 지연도 없다. 게임을 재미있게 만드는 데는 이게 방식 B보다 효과적인 경우가 많다.

> **정리하면** — 게임을 재미있게 하려면 C, 콘텐츠를 풍부하게 하려면 A, 정말 실시간 대화가 필요할 때만 B. **"AI를 넣었다"가 목적이 되면 대개 B를 고르고 실패한다.**

### 2.4 비용이라는 개념

지금까지 우리가 쓴 것은 전부 무료였다. GitHub Pages, Live Server, Supabase 무료 범위. 그런데 AI API부터는 다르다.

**알아 둘 것 세 가지**

1. **주고받은 글자량(토큰)에 따라 과금된다.** 호출 횟수뿐 아니라 **프롬프트가 길면 더 비싸다.** 사용자가 늘면 요금이 늘어나고, 내 게임이 인기를 얻으면 **내 돈이 나간다**
2. **상한을 걸어 둔다.** 대부분의 서비스에 사용량 한도와 알림 설정이 있다. **쓰기 전에 먼저 설정한다**
3. **무료 범위를 확인한다.** 어디까지 무료이고, 넘으면 막히는지 과금되는지 확인한다

> **가장 많이 당하는 사고** — 테스트 중에 반복 호출을 루프에 넣어 두고 잊는 것이다. 게임 루프 안에서 API를 부르면 **1초에 60번** 호출된다. 11장의 "랭킹은 게임 오버 시점에 한 번만"과 같은 원칙이다.

### 2.5 스스로 새로운 기술을 배우는 방법

이게 이 수업의 마지막 내용이고, 가장 오래 쓰일 내용이다.

앞으로 쓸 기술은 지금 모르는 것들이다. 그걸 배우는 절차를 정리하면 다섯 단계다.

```
1. 무엇을 할 수 있는지 먼저 본다   — 공식 문서 첫 페이지, 예제 화면
2. 가장 작은 예제를 돌려 본다       — "Hello World" 수준 하나
3. 그 예제를 조금 고쳐 본다         — 숫자 하나, 색 하나
4. 내 문제에 가장 가까운 예제를 찾는다
5. 내 코드에 조금씩 옮긴다          — 한 번에 하나씩, 매번 확인
```

**1~3단계를 건너뛰고 5단계부터 하는 것이 실패의 원인이다.** AI에게 "내 게임을 Phaser로 바꿔 줘"라고 하면 코드는 나온다. 그런데 안 돌아가면 손을 쓸 수 없다. 1~3단계를 거친 사람은 **최소 예제와 비교해서** 어디가 다른지 찾는다.

**공식 문서를 읽는 요령**

문서는 처음부터 읽지 않는다. 순서는 이렇다.

| 순서 | 볼 곳 | 목적 |
|---|---|---|
| ① | Getting Started / Quickstart | 가장 작은 예제 |
| ② | Examples / Demos | 뭘 할 수 있나 |
| ③ | 내 문제와 관련된 페이지 | 필요한 것만 |
| ④ | API Reference | 사전처럼. 찾을 때만 |

**버전과 날짜를 확인한다.** 블로그 글이나 영상은 오래된 것이 많다. **공식 문서를 먼저** 보고, 검색 결과는 날짜를 본다. AI의 설명도 오래된 방식일 수 있으니, **공식 문서와 어긋나면 문서를 따른다.**

**AI를 "가르치는 도구"로 쓰는 법**

10주 동안 AI는 주로 **대신 만들어 주는 도구**였다. 새 기술을 배울 때는 역할을 바꿔야 한다.

| ❌ 대신 해 달라고 | ⭕ 가르쳐 달라고 |
|---|---|
| "Phaser로 내 게임 만들어 줘" | "Phaser의 Scene이 내가 쓴 gameState와 어떻게 대응되는지 설명해 줘" |
| "이거 고쳐 줘" | "이 예제에서 이 줄이 없으면 무엇이 깨지는지 알려 줘" |
| "최신 방법 알려 줘" | "공식 문서 어디를 보면 되는지 알려 줘" |
| 코드를 받고 넘어간다 | **내가 아는 것에 연결해서** 설명을 받는다 |

오른쪽 열의 공통점은 **"내가 이미 아는 것과 연결해 달라"** 는 것이다. 10주 동안 쌓은 게임 루프·상태·충돌 판정이 **비교 기준**이 되기 때문에, 새 기술을 훨씬 빨리 읽을 수 있다.

**학습 루프**

```
작은 것을 돌린다 → 고쳐 본다 → 왜 그런지 묻는다 → 내 것에 옮긴다 → 커밋한다
```

7장의 디버깅 절차, 9장의 리팩터링 4원칙과 구조가 같다. **새로 배우는 것도 결국 같은 방식이다.**

### 2.6 다음에 무엇을 만들까

수업이 끝난 뒤 가장 흔한 실패는 **너무 큰 것을 고르는 것**이다. 기준 셋을 제안한다.

| 기준 | 설명 |
|---|---|
| **2주 안에 끝나는 크기** | 끝내는 경험이 실력보다 중요하다 |
| **내가 쓸 것** | 남을 위한 것보다 내가 매일 쓰는 것이 완성된다 |
| **지금 아는 것 + 새것 하나** | 전부 새로우면 못 끝낸다 |

게임이 아니어도 된다. 10주 동안 배운 것은 게임 전용이 아니다.

| 만들 것 | 쓰는 것 (이미 배운 것) |
|---|---|
| 내 수업 시간표 페이지 | HTML/CSS, localStorage |
| 과제 마감 타이머 | 루프, 상태, localStorage |
| 가계부 / 습관 체크 | 배열, 객체, 반복문, localStorage |
| 동아리 모집 페이지 | HTML/CSS, 배포 |
| 설문 결과 모으기 | fetch, Supabase (11장) |
| 두 번째 게임 | 전부 |

**두 번째 게임을 만들면 속도가 다르다.** 첫 게임의 7주가 두 번째에는 1~2주가 된다. 그게 10주의 결과다.

**저장소를 살려 둔다**

`my-game`은 지우지 않는다. 방학에 기능을 하나 더 붙이면 그대로 포트폴리오가 된다. 10주 동안 쓴 회고와 디버깅 기록이 함께 있으니, **"무엇을 어떻게 만들었는가"를 보여 줄 수 있는 저장소**는 생각보다 드물다.

## 3. 따라 하기 실습

> **⚠️ 오늘은 내 게임을 망가뜨리지 않는다.** 실습 1·2는 **별도 파일**에서 한다. 실습 3만 내 게임에 반영한다.
>
> **시작 전에 커밋한다.** 소스 제어 → `12장 시작 전 상태` → Commit.

### Step 1. Phaser 맛보기 — 별도 파일에서 (15분)

내 게임은 건드리지 않는다. 비교용 파일 하나를 만든다.

```
phaser-test.html 이라는 파일 하나를 새로 만들어 줘.
내 게임 파일들은 절대 건드리지 마.

- Phaser를 CDN으로 불러오는 한 파일짜리 예제로 만들어 줘
- 내용은 아주 단순하게: 사각형(또는 간단한 도형) 하나를 방향키로 움직이고,
  화면 밖으로 나가지 않게만 해 줘
- 물리 엔진을 켜서 중력과 바닥 충돌도 보여 줘
- 각 부분에 한국어 주석을 달고, 특히 아래 세 곳을 표시해 줘
  ① preload — 에셋을 미리 불러오는 곳
  ② create — 처음 한 번 실행되는 곳
  ③ update — 매 프레임 실행되는 곳 (내 게임의 gameLoop에 해당)
```

Live Server로 열어서 확인한다.

- [ ] 도형이 움직인다
- [ ] 바닥에 떨어져 멈춘다

**이제 비교한다.** 이 단계의 진짜 목적이다. 내 `script.js`를 옆에 열고, AI에게 묻는다.

```
내 script.js와 phaser-test.html을 비교해서 표로 정리해 줘.

내가 직접 만든 것 ↔ Phaser가 대신해 주는 것을 짝지어서,
아래 항목에 대해 각각 어느 코드가 그 일을 하는지 알려 줘.
- 게임 루프 / 그리기 / 입력 처리 / 충돌 판정 / 화면 전환 / 에셋 불러오기

그리고 Phaser를 쓰면 내가 잃는 것(직접 다룰 수 없게 되는 것)도 알려 줘.
```

**직접 확인할 것**

- [ ] `update()`가 내 `gameLoop`의 어느 부분에 해당하는지 짚을 수 있다
- [ ] Phaser에는 `clearRect`가 없다 — 왜 필요 없는지 알 수 있다
- [ ] 충돌 판정이 몇 줄로 줄었는지 확인한다

> 재미있으면 숫자를 바꿔 본다 (중력, 속도). **하지만 내 게임을 Phaser로 옮기지는 않는다.** 오늘은 비교까지다.

### Step 2. AI로 콘텐츠를 미리 만들어 넣기 (15분)

방식 A다. **키가 필요 없고, 비용도 지연도 없다.**

**(1) 콘텐츠를 생성한다** — AI 채팅에 직접 요청한다.

```
내 게임의 게임 오버 메시지를 만들어 줘.

게임: (제목 — 한 줄 설명)

- 점수대별로 나눠서, 아래 JSON 형식으로 만들어 줘
- 각 메시지는 20자 이내, 가볍고 긍정적인 톤으로
- 욕설이나 비하 표현은 쓰지 마

{
  "low":  ["(0~30점용 메시지 10개)"],
  "mid":  ["(31~80점용 10개)"],
  "high": ["(81점 이상용 10개)"]
}
```

**(2) 파일로 저장한다**

```
위 결과를 messages.json 파일로 저장해 줘. (내 게임 폴더에)
```

**(3) 게임에서 불러 쓴다**

```
게임 오버 화면에 messages.json의 메시지를 띄워 줘.

- 게임 시작 시 fetch로 messages.json을 한 번만 불러와 둬
  (게임 루프 안에서 부르지 말 것)
- 점수대에 맞는 배열에서 랜덤으로 하나 골라서 보여 줘
- 파일을 못 불러오면 기본 메시지 하나로 대체해 줘 (게임이 멈추면 안 돼)
- 한 판이 끝날 때마다 다시 고르게 해 줘
- 한국어 주석을 달아 줘
```

확인한다.

- [ ] 게임 오버마다 메시지가 바뀐다
- [ ] 점수대에 맞는 메시지가 나온다
- [ ] 콘솔에 에러가 없다
- [ ] **배포 후에도 작동한다** (JSON 파일을 커밋했는지 확인)

> **이게 "AI가 들어간 게임"이다.** 플레이 중에 AI를 부르지 않지만, 플레이어 경험은 달라진다. 11장의 키 문제도, 비용도, 지연도 없다.

### Step 3. 적을 똑똑하게 — 규칙 기반 AI (10분)

방식 C다. 내 게임에 반영한다.

```
적 중 하나(또는 새로운 적 한 마리)가 플레이어를 추적하게 해 줘.

- 플레이어 쪽으로 천천히 다가오게 해 줘 (플레이어보다 느리게)
- 일정 거리 안에 들어오면 조금 빨라지게 해 줘
- 추적 속도와 감지 거리는 변수로 코드 위쪽에 모아 줘
- 기존 적들의 동작은 그대로 두고, 추가만 해 줘
- 난이도가 너무 올라가면 안 되니, 추적하는 적은 한 마리만
```

**플레이해서 난이도를 조정한다.** 4~9장에서 한 튜닝과 같다.

- [ ] 적이 따라온다
- [ ] 피할 수 있다 (너무 빠르지 않다)
- [ ] 게임이 더 긴장된다

> **여기서 느낄 것** — 코드 몇 줄로 "생각하는 것처럼" 보인다. 이게 게임 AI의 실체다. 거대한 모델이 필요한 게 아니다.

### Step 4. 혼자 배우는 절차 연습 (10분)

**모르는 것 하나를 골라 2.5의 1~3단계만** 해 본다. 끝까지 만들지 않는다. **절차를 경험하는 것**이 목적이다.

고를 것의 예 — 지금 내 게임에 쓰지 않은 것 중 하나.

- 파티클 효과 (터지는 입자)
- 화면 흔들림(screen shake)
- 글꼴 바꾸기 (웹폰트)
- 간단한 애니메이션 (스프라이트 시트)
- 모바일 가상 조이스틱

절차대로 한다.

1. **검색한다** — 공식 문서나 MDN을 먼저 찾는다
2. **최소 예제를 돌린다** — 별도 파일(`learn-test.html`)에 만들어 본다
3. **숫자 하나를 고쳐 본다**

그리고 AI에게는 이렇게 묻는다. **코드를 받지 않는다.**

```
(배우려는 것)을 배우고 싶어.

1) 공식 문서나 믿을 만한 자료 어디를 보면 되는지 알려 줘
2) 가장 작은 예제가 어떤 모양인지 설명해 줘 (코드는 5줄 이내로만)
3) 내가 이미 아는 것(Canvas, 게임 루프, 이벤트) 중 무엇과 비슷한지 연결해서 설명해 줘

내 게임에 적용하는 코드는 주지 마. 내가 직접 해 볼 거야.
```

- [ ] 공식 문서 페이지를 찾았다
- [ ] 최소 예제가 작동했다
- [ ] 숫자를 고쳐서 변화를 봤다
- [ ] **내가 아는 무엇과 비슷한지 말할 수 있다**

### Step 5. 정리와 커밋 (5분)

1. `README.md`에 추가한다

```markdown
## 심화에서 추가한 것
- 온라인 랭킹 (11장, Supabase)
- 게임 오버 메시지 (AI로 사전 생성, messages.json)
- 플레이어 추적 적 (규칙 기반)

## 비교 실험
- phaser-test.html — Phaser 맛보기 (내 게임에는 적용하지 않음)
- learn-test.html — (배운 것) 최소 예제
```

2. 커밋 → Sync → **시크릿 모드로 배포 주소 확인**

## 4. 과제

### 과제 1. 세 가지 실습 결과 (필수)

- [ ] `phaser-test.html`이 저장소에 있고 작동한다
- [ ] `messages.json`이 있고, 게임 오버 메시지가 바뀐다
- [ ] 추적하는 적이 작동하고, 난이도가 조정되어 있다
- [ ] `learn-test.html`(Step 4의 최소 예제)이 저장소에 있다
- [ ] **내 게임이 여전히 정상 작동한다** (9장 `테스트목록.md`로 확인)

### 과제 2. 도구 비교표 (필수)

`my-game` 폴더에 **`비교.md`** 를 만든다.

```markdown
# 직접 만들기 vs 라이브러리

| 기능 | 내 코드 (어느 부분) | Phaser (어느 부분) | 줄 수 비교 |
|---|---|---|---|
| 게임 루프 | gameLoop() | update() | |
| 그리기 | ctx.fillRect 등 | | |
| 입력 처리 | keys 객체 | | |
| 충돌 판정 | checkCollision() | | |
| 화면 전환 | gameState 분기 | | |
| 에셋 불러오기 | img.onload | preload | |

## 내가 판단한 것
- 내 게임에 Phaser를 쓸 것인가 / 쓰지 않을 것인가:
- 그 이유:
- 어떤 게임이라면 Phaser를 쓸 것인가:
```

> **평가는 "Phaser를 썼는가"가 아니다.** **쓰지 않기로 한 판단에 근거가 있는가**를 본다. 9장의 미반영 판단과 같은 기준이다.

### 과제 3. AI 기능 설계 메모 (필수)

같은 파일 아래 또는 **`ai설계.md`** 에 쓴다. **만들지 않아도 된다. 설계만 한다.**

```markdown
# 내 게임에 AI를 넣는다면

## 넣고 싶은 기능
(예: 적이 플레이어의 패턴을 학습해서 반응한다 / 게임 오버 시 플레이를 평가해 준다)

## 세 방식 중 어느 것이 맞는가
| 방식 | 가능한가 | 이유 |
|---|---|---|
| A. 미리 생성 | | |
| B. 실시간 호출 (중간 서버) | | |
| C. 규칙 기반 | | |

## 방식 B를 고른다면 준비해야 하는 것
- 키를 어디에 두는가:
- 왜 브라우저에 둘 수 없는가:
- 비용 관리:
- 응답이 느리거나 실패할 때:
- 플레이어 입력을 그대로 AI에게 넘기면 안 되는 이유:

## 결론
(지금 내 게임에는 어느 방식이 맞는지, 왜)
```

> **마지막 항목 전의 다섯 질문이 평가의 핵심이다.** 11장의 키 문제를 스스로 연결해서 설명할 수 있는지를 본다.

### 과제 4. 다음 프로젝트 계획 (필수)

`회고.md`의 "다음에 만들고 싶은 것"을 구체화한다.

```markdown
## 다음 프로젝트 계획

- 만들 것:
- 왜 이것을 고르는가 (내가 쓸 것인가):
- 2주 안에 끝날 크기인가:
- 이미 아는 것:
- 새로 배워야 하는 것 (하나만):
- 첫 번째로 할 일 (가장 작은 단계):
```

> **"새로 배워야 하는 것"은 하나만 쓴다.** 둘 이상이면 2주 안에 끝나지 않는다.

### 과제 5. 선택 과제

- `messages.json`을 **적 이름이나 아이템 설명**으로도 만든다
- 추적하는 적에 **패턴을 하나 더** 넣는다 (일정 시간마다 멈춘다, 거리에 따라 방향을 바꾼다)
- `phaser-test.html`에 **내 게임의 한 장면만** 흉내 내 본다 (전체 이식은 하지 않는다)
- 방식 B를 **실제로** 시도한다 — 아래 네 가지를 **먼저** 갖춘 뒤에만 한다

  - [ ] 키는 **호스팅 서비스의 환경변수**에 넣는다. 코드 파일에 쓰지 않는다
  - [ ] 로컬에서 쓸 때는 `.env` 파일에 두고, **`.gitignore`에 `.env`를 추가**한다 (저장소는 Public이다)
  - [ ] AI 서비스 대시보드에서 **지출 상한과 알림**을 먼저 설정한다
  - [ ] 내 함수에도 **호출 제한**을 둔다 (간단한 토큰 검사나 분당 횟수 제한) — 함수 주소는 공개이므로 남이 마구 부를 수 있다

  그리고 배포 전에 11장 Step 6의 보안 점검을 다시 한다. **키를 한 번이라도 커밋했다면 먼저 재발급한다.**
- 두 번째 게임의 **기획서 한 장**을 3장 양식으로 써 둔다

### 과제 6. 회고 파일 (필수)

`회고.md`에 12주차를 추가한다. 양식은 **부록 E**와 같다.

- **1번:** Step 4에서 쓴 "가르쳐 달라" 프롬프트를 복사한다. **코드를 받지 않는 요청**이었는지 확인한다
- **2번:** 막힌 점. 이번 주는 **"Phaser 예제를 이해하려 할 때 막힌 것"** 이나 **"혼자 배우기 절차에서 어디가 어려웠는지"** 를 쓴다
- **3번:** 코드 설명. **이번 주는 비교 설명이다.** 내 코드의 한 부분과 Phaser의 대응되는 부분을 짝지어, 무엇이 같고 무엇이 숨겨졌는지 쓴다

## 6. 12주를 마치며

12주 전에는 코드 한 줄도 몰랐다. 지금 가진 것을 적어 보면 이렇다.

- 인터넷 주소가 있는 게임 하나
- 전체 랭킹이 돌아가는 서버 연결
- 지난 과정의 기록 — 회고, 디버깅 기록, 플레이테스트, 보안 점검
- 그리고 **다음에 만들 것의 계획**

그런데 가장 중요한 것은 목록에 없다. **모르는 것을 만났을 때 무엇을 해야 하는지 아는 것.**

```
작은 것부터 돌려 본다
망가뜨려 보고 원리를 확인한다
범위를 좁혀 원인을 찾는다
요청할 때 범위와 금지 조건을 함께 말한다
결과를 확인하고, 안 되면 되돌린다
남에게 시켜 보고 고친다
무엇이 여전히 위험한지 안다
```

이 일곱 개는 **JavaScript가 아니다.** 도구가 바뀌어도, AI가 더 좋아져도 그대로 쓰인다. 오히려 AI가 더 많은 것을 대신해 줄수록, **무엇을 요청하고 결과를 어떻게 판단할지 아는 사람**이 더 필요해진다.

0장에서 바이브 코딩을 이렇게 정의했다.

> 타이핑을 대신해 주는 것이지, 이해를 대신해 주는 것이 아니다.

12주 동안 그 차이를 직접 겪었을 것이다. AI가 쓴 코드가 안 돌아갈 때, 설명할 수 없는 코드가 쌓였을 때, 남이 내 게임을 못 했을 때. 그때마다 이해해야 했던 사람은 여러분이었다.

그 몫은 앞으로도 여러분의 것이다. 그리고 그게 이 수업에서 가장 쓸모 있는 결과물이다.

수고했습니다. 🎉

## 이번 주 자주 막히는 지점

| 증상 | 원인과 해결 |
|---|---|
| Phaser 예제가 아무것도 안 뜬다 | CDN 주소 오타 / 콘솔 첫 에러 확인 / 버전이 맞는지 |
| Phaser 예제가 내 게임을 덮어썼다 | **되돌린다.** 별도 파일에서 하라고 한 이유다 |
| Phaser 코드가 전혀 이해되지 않는다 | **정상이다.** 오늘은 "무엇을 대신해 주는가"만 알면 된다 |
| `messages.json`을 못 불러온다 | 파일명·경로 확인 / Live Server로 열었는지 (파일 직접 열기로는 막힌다) |
| 배포하니 메시지가 안 나온다 | JSON 파일을 **커밋**했는지 / 파일명 대소문자 |
| JSON 문법 에러가 난다 | 마지막 쉼표, 따옴표 짝. AI에게 "이 JSON 문법을 검사해 줘" |
| 메시지가 매번 같다 | 랜덤 선택이 한 번만 실행된다. 게임 오버마다 다시 고르게 한다 |
| 추적하는 적을 피할 수 없다 | 추적 속도가 플레이어보다 빠르다. **반드시 더 느리게** |
| 적이 플레이어에 딱 붙어 떨린다 | 일정 거리 이내에서는 멈추게 하거나, 최소 거리를 둔다 |
| 게임 루프에서 API를 불러 요금이 나갔다 | **1초에 60번 호출된다.** 호출은 상태가 바뀌는 시점에만 |
| AI가 Phaser로 전체 이식을 해 줬다 | 요청에 "내 게임 파일은 건드리지 마"를 넣는다. 되돌린다 |
| 공개 API를 불렀는데 CORS 에러가 난다 | 그 서버가 브라우저 호출을 허용하지 않는 것이다. **내 코드로는 못 고친다** — 허용하는 API로 바꾼다 |
| AI 키를 코드에 썼다 | 즉시 재발급하고, 환경변수로 옮긴다. `.env`는 `.gitignore`에 넣는다 |

모르는 용어는 **부록 C**, 오류는 **부록 D**, 프롬프트는 **부록 B**를 본다.
